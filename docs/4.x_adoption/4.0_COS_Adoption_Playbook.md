# Context OS Adoption Playbook
## Version 2.0
Last Updated: 2026-09-06
Owner: Context OS Maintainers
Status: Canonical adoption model

## Start with one work need

Adoption should make a bounded piece of work easier to orient, govern and
verify. Begin with the need, existing source authority and a measurable
baseline. A symptom checklist, document count or fixed number of weeks does
not establish fit or value.

Current product status is [design-partner alpha](../5.x_strategy/5.6_COS_Current_Product_Definition.md).
A technical operator can run the local diagnostics; independent adoption,
mapping and repeat operation still need proof. The previous v1.0 Playbook's
mandatory normalization sequence, fixed timelines and benefit promises are
superseded by this model. They were proposed guidance, not measured results.

## Select the adoption path

| Starting situation | First move | Runtime path | Completion boundary |
|---|---|---|---|
| GREENFIELD | Declare one purpose, accountable owner, work need and unknowns | Assess available context; optionally choose native templates and governed bootstrap; use assisted Construction for missing content | Created skeletons are not verified facts; source owner must review content |
| EXISTING ORGANIZED | Inventory current intent, work, policy and evidence sources in their existing locations | Govern an External Adoption Profile, then use profile-aware diagnostics and Activation | No folder migration, renamed artifacts or duplicate SSOT; mappings need authority/currentness evidence |
| EXISTING FRAGMENTED | Map supported sources and expose missing owners, conflicting lifecycle or stale evidence | Use partial mappings and scoped assessments; resolve only blockers to the chosen work | Unknown does not become missing, unowned, approved or safe; accountable humans resolve ambiguity |

Native bootstrap and External Adoption Profile mapping are different paths.
Neither is a mandatory prerequisite for the other. Both preserve the
organization's source-of-record authority and separate read permission from
write permission. A native [MOM](../3.x_operation/3.0_COS_Minimum_Operational_Map.md)
is a useful formation pattern, not a filename requirement for an existing
organization.

## Smallest coherent journey

| Step | Operator task and available Runtime support | Gate / evidence |
|---|---|---|
| Scope and map | Select one need and authorized local source scope; identify current sources, owners, precedence and gaps | Accountable mapping decision; no inferred owner or private system access |
| Assess | Use assess and validate, with the approved profile for existing canon | Review applicability, blockers and unknowns; native Readiness scores are not target maturity |
| Prepare working context | Resolve blocking context gaps; activate a bounded package/handoff and check it | Goal, selected source hashes, authority, exclusions and gaps are inspectable; human confirms orientation |
| Work and record | Execute a separately authorized Mission using the brief; retrieve only additional needed evidence | Record extra retrieval, actual use, outcome and procedural/strategic intervention; Runtime does not execute work |
| Review and reuse | Use health, authorized memory and advisory reasoning; check changed sources before consequential reuse | Accept outcomes; distinguish historical identity from current eligibility; promote learning only through governed change |

This is a product journey over existing primitives, not a new command, object
family or orchestrator. Bootstrap and Construction appear only when scoped
context must be formed. Measurement begins on the first attempt, including
setup/mapping effort and failed attempts.

## External profile preparation

The [External Adoption Profile Contract](../1.x_architecture/1.5_runtime_contracts/1.5.16_External_Adoption_Profile_Contract.md)
requires explicit target identity, mapping ownership/authority, source
locators, supported versus unknown mappings, validation applicability,
required Activation concepts, evidence isolation and invalidation conditions.
The current adapter resolves repository-relative local paths; remote system
locators are not implemented connectors.

Preparation is currently a human-reviewed JSON task. A design partner helps
translate target semantics without inventing truth. The target owner decides
what governs and what may be exposed. The bundled Lukspeed example documents
one historical mapping; it is not a generic template, current target proof or
permission to inspect Lukspeed. Each new target needs its own evidence.

Use the profile consistently with validate, assess, activate, health, memory
and reason. Changing its meaning invalidates affected current derivatives.
The init/apply chain has no profile flag: do not run native bootstrap to
“repair” a mapped organization merely because it lacks Context OS folders.

Memory requires a separately applicable retention/visibility policy. Profile
mapping alone never permits exposure. Detailed Work Ownership protection
requires explicit work items, exact need references, source/coverage evidence
and optional lifecycle semantics through the Python API; it is not automatic
with a profile or CLI command.

## Assistance and self-service gate

Maintainers currently help with source mapping, applicability, API composition,
policy/evidence preparation, interpreting uncertain reports and re-anchoring.
Accountable source owners must supply intent, precedence and authority even
when procedural assistance is removed.

Self-service requires an independent technical operator to complete and repeat
the narrow journey from published guidance, including a failed/blocked state
and material source change, without undocumented code or maintainer rescue.
See the [minimum operator experience](../5.x_strategy/5.6_COS_Current_Product_Definition.md#product-experience-boundary)
and [value measurements](../5.x_strategy/5.6_COS_Current_Product_Definition.md#value-proof-framework).
No current command proves this gate simply by returning exit 0.

## Where to begin

Try the read-only [local installation walkthrough](4.5_COS_Runtime_Installation.md).
Then qualify one use case under the [Productization Roadmap](../../SSOT/P.2_Product_Roadmap.md#post-v1-productization-roadmap).
Do not start with connectors, orchestration, a complete documentation migration
or organization-wide transformation.
