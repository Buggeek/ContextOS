implementation begins under Codex (or any external implementer). It mirrors
the **Codex Transition Criteria** declared during the Pre-Codex Operational
Consolidation and is published here as a durable adoption artifact.

If any item below is `false`, code implementation **must not** start; instead,
a new mission must close the gap.

## Codex Implementation Order (recommended)

Once this checklist is fully `true` and `v0.2.1-pre-codex` is tagged, the
historical recommended order for Codex implementation in the original v0.3
Runtime Foundation plan was:

1. **EPIC-007 Validator Engine** — establishes the contractual gate every
   other component will consult.
2. **EPIC-008 Runtime CLI** — provides the uniform surface for invoking
   discovery, builder, validator, and activation.
3. **EPIC-004 Discovery Engine v0** — produces the first structured
   external input the rest of the Runtime can build on.
4. **EPIC-006 Context Builder v0** — composes Discovery output into MOM
   drafts and promotes them under governance.
5. **EPIC-005 Knowledge Engine v0** — extends the Builder's input with
   inferred drafts from unstructured corpora.

After the roadmap realignment, product execution is no longer epic-by-epic.
The next release objective is Context Readiness: an assessment that answers
what context exists, what is missing, and what should happen next. The
canonical contract is
[`1.5.6 Context Readiness Assessment`](../1.x_architecture/1.5_runtime_contracts/1.5.6_Context_Readiness_Assessment_Contract.md).
