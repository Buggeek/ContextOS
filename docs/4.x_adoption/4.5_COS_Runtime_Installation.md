## Current installation: a local checkout

The available product is a [design-partner alpha](../5.x_strategy/5.6_COS_Current_Product_Definition.md).
Install the Runtime checkout separately from the organizational sources you
want to assess. Current implementation uses Python standard-library modules;
Git is used for repository identity/currentness evidence. Python 3.9.6 and Git
2.50.1 on macOS were exercised in the rebaseline. Python 3.9 or later is the
source-level prerequisite; no wider platform/support matrix is proven here.
No package-manager distribution, daemon, container deployment or hosted
installation is established by this guide.

```bash
git clone https://github.com/Buggeek/ContextOS.git
cd ContextOS
./contextos --version
./contextos --help
./contextos validate --root . --mode gate
./contextos assess --root .
./contextos activate --root . --goal "Orient one bounded Mission" --handoff
./contextos health --root .
```

This evaluates Context OS's own repository. It is a diagnostic demo, not proof
that a new organization has been adopted. Reports may contain warnings,
attention or unknown states while the process exits 0. Read the findings and
selected sources. Activation prepares context; it does not execute the work.

## Evaluate your authorized local sources

Choose the [native or external path](4.0_COS_Adoption_Playbook.md) first.
For a native-format target, use the Runtime checkout's absolute contextos
executable path with --root pointing to that target. Bare init only plans
native bootstrap; see [the complete approval/apply chain](../../tools/bootstrap/README.md)
before considering any writes. The CLI has no profile-aware init/apply mode.

For an existing organization, an accountable mapping owner must prepare and
review that target's own [Adoption Profile](../1.x_architecture/1.5_runtime_contracts/1.5.16_External_Adoption_Profile_Contract.md).
The following paths are placeholders to replace with authorized local inputs;
they are not executable examples against a bundled target:

```bash
./contextos assess --root /path/to/authorized-target --adoption-profile /path/to/approved-profile.json
./contextos activate --root /path/to/authorized-target --adoption-profile /path/to/approved-profile.json --goal "Orient one bounded Mission" --handoff
```

Bind that same profile to validate, health, memory and reason. Mapping does
not authorize target access, publication or mutation. Do not use the Lukspeed
fixture as a generic profile or as current target authority.

## Results, persistence and recovery

The [actual CLI](../../tools/cli/contextos_cli.py) has seven commands:
validate, assess, init, activate, health, memory and reason. Each supports
--help. Diagnostic commands and bare init leave canonical target files alone;
--json-out explicitly writes the requested report file. Store derived reports
in a caller-controlled evidence location, not as replacement target canon.

```bash
./contextos activate --root . --goal "Orient one bounded Mission" --json-out /tmp/contextos-orientation-package.json
./contextos activate --root . --check-package /tmp/contextos-orientation-package.json --handoff
./contextos memory --root . --goal "Find governed prior art"
./contextos reason --root . --goal "Identify context requiring attention"
```

Before reusing a saved package/handoff, run its check and inspect gaps.
Materially changed governing sources require fresh context. Preserve the prior
object as historical evidence; do not overwrite its identity to make it pass.
Memory without applicable policy may return zero exposed items. Reasoning
is advisory and unknown inputs cannot become authority.

| Result | Meaning |
|---|---|
| 0 | Command completed without its blocking conditions; not semantic sufficiency, useful work or organization readiness |
| 7 | Blocking finding, invalid saved evidence or unmet gate; inspect the report |
| 8 | Fatal Validator finding where applicable |
| 9 | Runtime CLI/configuration error handled by the command |
| 2 | Argument-parser rejection, including unknown command/flag |

validate --mode install-check exists but only evaluates its configured local
Validator rules. health is an on-demand Context Health report; it is not a
service availability, credential, source connectivity or installer check.

# Historical installation contract (not executable current guidance)

## Purpose

This document defines the **installation perspective** of the Context OS
Runtime: prerequisites, supported environments, installation modes, the
installer contract, and post-installation verification.

It is the operator-facing companion to
[`4.4_COS_Runtime_Bootstrap.md`](4.4_COS_Runtime_Bootstrap.md). Installation
makes the Runtime *available*; Bootstrap makes it *operational*.

---

## Scope

Installation covers the steps required so that the Bootstrap flow can begin:

```
Install   →   Bootstrap   →   Activate   →   Operate
(4.5)         (4.4)           (3.4 §8)        (3.4 §3..§9)
```

This document does **not** specify implementation. It specifies the
**installation contract** that the Runtime CLI (EPIC-008) must satisfy.

---

## Prerequisites

### Organizational
- A declared Runtime Owner (human).
- A declared initial governance roster: Maintainer, Product Owner, Runtime
  Owner.
- Acknowledged commitment to the principles defined in
  [`0.3_COS_Principles.md`](../0.x_foundations/0.3_COS_Principles.md).

### Technical
- A version-controlled repository for the SSOT (Git).
- Network access to declared source systems.
- A credential store for source credentials.
- A target environment for the Runtime services (local workstation,
  container, or hosted environment).

### Documentation
- An organizational intent statement (vision draft or rough equivalent).
- A source inventory (repositories, document corpus, services).

## Installation Steps

### Step 1 — Initialize

Operator runs the canonical entry point:

```bash
contextos init
```

**Current v0.4 effects:**
- Produces a read-only Guided Bootstrap plan.
- Explains what would be created, what already exists, what is blocked, and
  what requires human action.
- Does not create scaffolding, write a Runtime manifest, or read external
  systems.

**Idempotent:** safe to re-run; no repository files are modified.

Write-capable initialization is a future approval/apply slice and must not be
implied by bare `contextos init`.

### Step 2 — Configure Sources

Operator declares connectable sources (used by Bootstrap Step 1):

```bash
contextos sources add <type> <reference>
```

**Effects:**
- Appends to the Connector Manifest.
- Records credential references (not values).
- Validates connectivity.

### Step 3 — Configure Governance

Operator declares the initial governance roster:

```bash
contextos governance set-roster --maintainer <id> --product-owner <id> --runtime-owner <id>
```

**Effects:**
- Writes governance roster to Runtime manifest.
- Initializes Authority Model bindings per
  [`3.6`](../3.x_operation/3.6_COS_Human_Agent_Authority_Model.md).

### Step 4 — Verify Installation

```bash
contextos health
```

**Effects:**
- Runs the Validator Engine in `install-check` mode.
- Confirms scaffolding integrity, manifest validity, governance roster
  presence, and source reachability.
- Produces an installation report.

### Step 5 — Hand Off to Bootstrap

When `contextos health` passes, the Runtime is **installed but not
operational**. Bootstrap (4.4) takes over.

---

## Post-Installation Verification

A correctly installed Runtime instance satisfies all of:

- [ ] `SSOT/`, `docs/`, `ops/`, `templates/` folders exist with canonical
      structure.
- [ ] Runtime manifest declares mode, version, owner.
- [ ] Connector Manifest exists (may be empty).
- [ ] Governance roster declared.
- [ ] `contextos health` exits 0 in `install-check` mode.
- [ ] No agent is yet activated.
- [ ] No autonomy is yet granted above L1.

If any item fails, installation is incomplete; Bootstrap must not start.

## Installation Contract (for EPIC-008)

The Runtime CLI must expose these commands with the semantics defined above:

| Command | Purpose | Failure exit code |
|---|---|---|
| `contextos init` | Produce read-only Guided Bootstrap plan | 0 / 7 / 8 / 9 |
| `contextos sources add` | Register a source in Connector Manifest | 2 |
| `contextos sources list` | List registered sources | 0 |
| `contextos governance set-roster` | Set initial governance roster | 3 |
| `contextos health` | Validate installation or runtime state | non-zero per rule |
| `contextos scan` | Bootstrap Step 3 (Discovery) | 4 |
| `contextos build-mom` | Bootstrap Step 6 | 5 |
| `contextos build-ssot` | Bootstrap Step 7 | 6 |
| `contextos validate` | Bootstrap Step 8 | 7 |
| `contextos activate` | Bootstrap Step 9 + Step 10 | 8 |

Detailed I/O shapes belong to the **CLI Contract** in
[`docs/1.x_architecture/1.5_runtime_contracts/`](../1.x_architecture/1.5_runtime_contracts/).

## Upgrade Path

Upgrades are governed by the Runtime Lifecycle (3.4 §8). Minimal rule:

1. New Runtime version must declare a **maturity floor** equal to or higher
   than the current instance.
2. Upgrade dry-run produces a diff report against the current Runtime
   manifest.
3. Upgrade is recorded in the Accountability Ledger.

---

## Anti-Patterns

- Installing on top of a non-version-controlled SSOT directory.
- Granting autonomy above L1 during installation.
- Connecting sources before declaring governance roster.
- Bypassing `contextos health` to start Bootstrap.
- Treating installation as one-time; it is part of the Runtime Lifecycle.
