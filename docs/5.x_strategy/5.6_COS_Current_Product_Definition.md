# 5.6 - Context OS Current Product Definition

Version: 1.0
Last Updated: 2026-09-06
Owner: Context OS Maintainers
Status: Canonical product baseline

## Product definition

**Category:** Organizational Context Runtime, unchanged from
[GENESIS](../0.x_foundations/0.8_COS_GENESIS.md).

**Today:** a local, deterministic Python Runtime with seven CLI commands and
additional Python engine APIs. It checks visible context, prepares bounded
working context for a Mission, preserves source identity and authority
boundaries, and produces governed health, memory and reasoning reports.
Native Bootstrap and Builder can perform explicitly approved create-only
writes; diagnostic reports do not authorize work.

**Current designation: design-partner alpha.** The Runtime is functional and
available to developers from the repository. Adoption beyond maintainers
requires technical integration and accountable mapping/policy decisions.
Independent self-service adoption has not been demonstrated. This designation
does not change the historical v1.0 release or its software version.

**Current target user:** a technical maintainer, founder or operator able to
use Git, a terminal, JSON, and Python APIs when the CLI is insufficient.

**Current target organization:** a software team with readable, scoped local
files representing intent, work, authority and evidence, and a human who can
identify their owners and currentness. These files may be distributed across
the target repository; a Context OS-native SSOT tree is optional. Evidence
does not establish arbitrary multi-system or non-Technology operation.

**Immediate problem:** before bounded work begins, governing context is hard
to reconstruct and distinguish from obsolete records, suggestions and action
authority. This risks missing constraints or proposing work already owned.

**Current value:** inspectable selection, provenance, integrity findings,
unknowns, and explicit authority/currentness checks. Historical external
mapping removed false native-structure blockers and manual source nomination.
Lower total cognitive burden, faster delivery and business value remain
unproven; added evidence can also increase report-reading work.

**Current wedge:** orient one bounded Mission over an existing team's canon:
identify the governing sources, show what is missing or requires a decision,
and provide a checked working brief without reorganizing the target first.
Optional Work Ownership protection requires explicit API inputs and coverage;
it is not automatically provided by every CLI reasoning run.

**Long-term outcome:** Context OS enables AI-native organizations to govern
their own evolution. This is the outcome to pursue and test, not evidence that
every installation already delivers it.

## What can be used now

| Surface | Available behavior | Practical boundary |
|---|---|---|
| validate / assess | Integrity findings and scoped context readiness | Rule coverage is bounded; readiness does not certify an organization |
| init | Native plan/proposal/approval/acceptance/preflight/apply chain | Bare command reads only; approved apply creates missing artifacts, not verified organizational facts |
| activate | Bounded package, compact handoff and saved-result checks | Does not start agents, services or work; semantic sufficiency still needs evidence |
| health | On-demand integrity, usefulness limits and learning candidates | Usefulness remains unknown without supplied use evidence; no background monitoring |
| memory | Policy-aware prior-art retrieval | Missing policy can legitimately expose nothing; history grants no current authority |
| reason | Structured advisory assessment and saved checks | Deterministic evidence composition, not autonomous decision-making |
| Python engines | Discovery, Construction, Builder, Context Versions, Mission-use, Work Ownership | Expert integration; no equivalent end-to-end CLI flow or automatic evidence capture |
| External profile binding | validate, assess, activate, health, memory, reason | Hand-authored governed JSON and local target files; no profile-aware init/apply |

Current boundaries exclude task/project-management replacement, automatic
owner discovery, implicit target write authority, connector ingestion,
semantic certification, general document interpretation, hosted services,
background capture, destructive retention and autonomous canonical mutation.

The experimental frontier includes semantic sufficiency, useful reasoning,
transfer of ownership/lifecycle mappings, repeatable memory reuse and
cross-domain value. These are hypotheses even where a deterministic primitive
already exists.

## User and adoption truth

“Possible with assistance” is a fit hypothesis, not a supported market segment.
No segment below has demonstrated end-to-end self-service adoption.

| Person / organization | Usable today? | Self-service? | Design-partner assistance | Prerequisites and available value | Major blockers / evidence limit |
|---|---|---|---|---|---|
| Context OS maintainer / developer | Yes, local Runtime and self-hosting | Can run tools independently; adopter self-service not proved by maintainers | Usually supplies the assistance | Repo/code familiarity; explicit authority; inspectable governed work | Internal knowledge hides setup and procedural costs |
| Technical solo founder | Bounded evaluation is plausible | CLI demo possible; complete adoption unproven | Required for a supported adoption attempt | Git/terminal, bounded goal, source authority; orientation and gaps | No independent founder onboarding study; policy/API burden |
| AI-native startup / small software team | Best current design-partner fit | Not demonstrated | Yes | Shared readable canon and accountable owner; bounded Mission context | Only one external Technology reference; repeat operation/value unproven |

| Non-technical organization | No supported independent journey today | No | Research/design partner needed even to qualify a slice | Technical operator and local evidence representation | No external non-Technology adoption evidence; no normal end-user experience |

## Product experience boundary

Normal users should understand their goal, governing sources, permission
boundary, blocking gaps, next action and observed result. They should not have
to reconstruct Runtime object chains to make routine use of the product.

| Concept | Product exposure decision | Reason |
|---|---|---|
| Context Version | Internal Runtime primitive; advanced operator provenance; exposed developer API | A user needs “what changed / can I reuse this?”, not hash construction |
| Activation Package | Internal primitive and developer surface | Source/goal binding should support a brief without becoming a separate SSOT |
| Handoff | Normal user-facing working brief; binding/check details advanced | Directly communicates goal, sources, gaps and bounds |
| Mission-use evidence | Internal evidence model; developer input; advanced operator review | Normal user records outcome/extra work, not schema assembly |
| Retention Resolution | Internal policy evaluation; advanced accountable operator policy | User needs why memory is unavailable; defining policy still belongs to humans |
| Work Ownership Resolution | Internal gate and exposed developer API | User needs “existing work owns this / ownership unknown”; exact input preparation is not a normal user task |
| Adoption Profile internals | Advanced mapping-owner/operator concept and developer surface | Normal user sees mapped sources and unresolved authority, not JSON internals |

Before **self-service** is claimed for the narrow wedge, independent technical
operators must complete setup, select the correct adoption path, map or form
the minimum context, interpret blocked/unknown results, obtain and check a
working brief, perform separately authorized work, record its outcome and
repeat after a material source change. Routine steps must be possible from
published guidance without private maintainer scripts, undocumented API
assembly or founder procedural rescue. Human strategic and authority decisions
remain normal and must not be counted as product failure.

The minimum operator experience needs one coherent explanation of current
state, source scope, next action and recovery; inspectable detailed evidence;
clear persistence/recheck instructions; and a supported path for mapping,
policy and outcome inputs. A dashboard, chat UI, conversational canvas or new
mega-command is not a prerequisite. The smallest surface should be chosen
from observed operator failures.

## Value-proof framework

Each claim must name scope, baseline, comparable Mission class, operator,
Runtime/profile/source versions, observation window, numerator/denominator,
missing observations and limitations. Record failures and additional work,
not just successful cases. Predeclare improvement targets with the reference
owner before collecting comparative results. There is no aggregate score and
no default inference from fewer bytes, green checks or one prevented proposal.

| Value class | Minimum acceptable evidence | Current state |
|---|---|---|
| CORRECTNESS VALUE | Reproducible case, expected behavior, negative cases, observed result | Tests and bounded Runtime integration support correctness within tested scopes |
| AUTHORITY / GOVERNANCE VALUE | Trace an actual decision/action to source, human authority, check and acceptance; count violations/escapes | Self-hosting, profile isolation and bounded external docs evidence; not enterprise assurance |
| CONTEXT QUALITY VALUE | Compare governing-source relevance, sufficiency, false blockers and missed constraints against owner-reviewed ground truth | Profile repeat corrected native false blockers and selection in one target; broader quality unproven |
| COGNITIVE-BURDEN VALUE | Comparable orientation and retrieval effort, procedural interventions, interpretation effort and reported burden | Partial orientation proxy evidence; no causal total-burden result |
| EXECUTION VALUE | Comparable completed Missions, duration, first-pass success and context-induced rework with confounders | Not yet demonstrated |
| BUSINESS / USER VALUE | Accepted delivered outcome plus observed user/business effect and attribution limits | Not yet demonstrated; documentation coherence is not downstream product value |

### Lukspeed Reference Implementation #1 gate

Repository-held evidence comprises a failed native pilot, a profile-aware
read-only repeat and supplied accepted evidence of one docs-only Mission.
It does not establish current target state or blanket target authority.

Before stronger product claims, a separately authorized reference program must:

1. Establish fresh target/profile/authority and material-source checks without
   replacing target canon; declare retention/visibility policy where memory
   benefit is tested. Unknown ownership mapping remains a blocker for that use.
2. Predeclare comparable baseline and success thresholds for at least three
   bounded real Product or Engineering Missions. This is a proposed minimum
   repeatability gate, not a statistically representative sample or existing
   result. Include one return after material context change and one evidenced
   prior-art/ownership case; record failures and excluded cases.
3. Compare orientation, retrieval burden, procedural versus strategic help,
   first-pass success and rework; preserve decision/evidence traceability.
   Account for Mission complexity, operator familiarity and maintainer help.
4. Obtain target-owner acceptance of the work and at least one observed
   user/product outcome before claiming downstream value. If only governance
   improved, claim governance benefit only.
5. Have an operator other than the Context OS maintainer repeat the narrow
   journey; state remaining assistance. Publish only the bounded claims the
   measurements support, with target-authorized evidence disclosure.

This document defines gates only. It authorizes no Lukspeed access or Mission.

## Second reference organization gate

A second organization tests transfer of the model and product experience,
not repetition of Context OS self-hosting or the same founder's software
workflow. Qualify it after a usable narrow adoption path and reference #1
measurements exist. Small discovery hypotheses can be recorded earlier;
starting target work still requires its own authority.

A useful reference must have an independent operator and governance owner,
different ownership/lifecycle conventions and a bounded recurring work need.
Prefer a non-Technology operation or a non-repository source of record. The
source access/export must preserve authoritative provenance; manually curated
local exports test representation only, not live connector behavior.

Require supported/unknown concept mapping, explicit policy and source scope,
baseline and repeated outcomes, source-change/re-anchor evidence, recorded
procedural assistance, and an account of which Context OS assumptions failed.
No target-specific core logic or imposed native folder migration may hide a
transfer failure. Missing generalization is valid evidence. Two organizations
still do not establish universality, enterprise readiness or product-market fit.
No organization is selected or contacted by this Mission.

## Unresolved questions

How much effort does a new operator need to author/review a valid profile?
Which subset of evidence/policy preparation must be productized for the wedge?
What is the false-negative rate of lexical selection and exact ownership
matching in real work? Can policy-authorized memory improve a decision rather
than merely return prior art? Does a second operation preserve meaningful
authority without artificial repository restructuring? What platform/support
commitment is justified by actual adopters?

These questions are inputs to the [Productization Roadmap](../../SSOT/P.2_Product_Roadmap.md#post-v1-productization-roadmap),
not hidden claims or automatic execution authority.
