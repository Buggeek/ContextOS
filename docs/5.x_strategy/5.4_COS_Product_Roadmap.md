# 5.4 — Context OS Product Roadmap

## Purpose

This document defines the evolution roadmap of Context OS from governed
framework to Organizational Context Runtime.

The canonical architecture definition is
[`1.0 Context OS Architecture`](../1.x_architecture/1.0_COS_Architecture.md).

The roadmap is organized around user-visible product outcomes, not subsystem
completion. Epics remain durable capability pools, but releases now ship the
smallest coherent slices needed to move users through the Context OS journey.

---

# Canonical Product Journey

```text
Assess -> Bootstrap -> Construct -> Activate -> Learn -> Reason
```

| Step | User question | Product job |
|---|---|---|
| Assess | What context exists here, what is missing, and what should I do next? | Produce a Context Readiness Assessment |
| Bootstrap | How do I create the minimum governed Context OS home? | Guide setup without guessing truth |
| Construct | How do I turn sources into usable context? | Produce reviewable MOM and SSOT artifacts |
| Activate | How does context reach the tools and agents where work happens? | Surface context in operational environments |
| Learn | How does context stay current? | Detect drift, capture learning, recommend remediation |
| Reason | How does context improve decisions and execution? | Support governed contextual reasoning |

---

# Product Evolution

```text
Framework
    ↓
Governed Framework
    ↓
Context Readiness
    ↓
Guided Bootstrap
    ↓

```

---

# Release Principles

- Release goal beats epic completion.
- Every release must demonstrate visible user value.
- Runtime components are introduced only when they support the current journey
  step.
- Validator and CLI remain stable compatibility rails.
- Discovery must produce structured output before Builder promotes context.
- Knowledge Engine work begins after the product has a clear structured
  context path.
- Context OS must dogfood each release against this repository.

# Version v0.3

## Context Readiness

Product Goal:

Transform an existing repository into an understandable Context OS readiness
state through the canonical
[`Context Readiness Assessment`](../1.x_architecture/1.5_runtime_contracts/1.5.6_Context_Readiness_Assessment_Contract.md).

Primary User Outcome:

A user can run a local assessment and receive a human-readable and
machine-readable report explaining:

- what Context OS artifacts exist
- what context is missing
- what governance and ownership gaps exist
- what next actions are recommended

Included Epic Slices:

- Context Readiness Assessment Contract: dimensions, scoring, readiness
  levels, report schema, and recommendation taxonomy.
- EPIC-007 Validator Engine: reuse the shipped ValidatorEngine as the
  structural and governance signal source.
- EPIC-008 Runtime CLI: expose the readiness workflow through the CLI while
  preserving `contextos validate`.
- EPIC-004 Discovery Engine: local repository inventory slice only.
- EPIC-006 Context Builder: recommendation mapping only; no SSOT mutation.

Deferred Capabilities:

- external connectors
- full Discovery Bundle
- Knowledge Engine interpretation
- `build-mom` / `build-ssot`
- IDE activation
- agent runtime
- Context Graph runtime

Definition of Done:

- `contextos assess` produces a Context Readiness Assessment in human and
  JSON formats conforming to `contextos.readiness.report/1`.
- Assessment is read-only and deterministic enough for local comparison.
- Current repository can dogfood the assessment.
- Validator gate remains passing.
- Report recommends the next bootstrap or remediation actions.
- Recommendations use the canonical readiness recommendation taxonomy.

# Version v0.4

## Guided Bootstrap

Status: Released as `v0.4.0-guided-bootstrap`

Product Goal:

Turn readiness output into the minimum governed Context OS home.

Primary User Outcome:

A first-time user can move from assessment to a configured local Context OS
workspace without hand-assembling required structure.

Included Epic Slices:

- EPIC-008 Runtime CLI: bootstrap-oriented commands and help surfaces.
- EPIC-006 Context Builder: governed bootstrap planning, proposal, approval,
  preflight, create-only apply, validation, and evidence path.
- EPIC-007 Validator Engine: pre-bootstrap and gate checks.
- EPIC-004 Discovery Engine: readiness inventory reuse where needed for
  bootstrap.

Deferred Capabilities:

- broad connector ecosystem
- full SSOT promotion automation
- Knowledge Engine
- IDE activation
- agent runtime

Definition of Done:

- Readiness report can drive a guided bootstrap path.
- Generated or proposed artifacts are clearly marked as drafts or hypotheses.
- Governance roster and ownership requirements are visible before promotion.
- Bootstrap can be repeated safely on an unchanged repository.

# Version v0.5

## Context Construction

Status: Released

Product Goal:

Produce reviewable Context OS artifacts from structured repository and source
signals.

Primary User Outcome:

A user can construct or update MOM and SSOT drafts from discovered signals
with provenance and governance controls.

Included Epic Slices:

- Context Construction Planning: convert readiness, inventory, validator, and
  bootstrap evidence into governed construction candidates without writing
  files or promoting truth.
- EPIC-004 Discovery Engine: read-only local Discovery Bundle v0 before
  external connectors or scan CLI.
- EPIC-006 Context Builder: read-only Builder Draft Plan and Draft Authority
  Contract, Draft Workspace decision/runtime preflight, controlled create-only
  draft writes, read-only draft review, governed Review Decision, and governed
  Approval Decision, read-only Promotion Preflight, and controlled create-only
  promotion before replacement promotion/canonicalization expansion.
- EPIC-007 Validator Engine: promotion gate integration.
- EPIC-008 Runtime CLI: existing readiness/bootstrap validation surfaces remain
  stable; construction command surfaces are deferred.

Deferred Capabilities:

- full Knowledge Engine interpretation
- long-lived watchers
- full Context Graph runtime
- autonomous promotion
- construction CLI workflow
- governed replacement promotion

Definition of Done:

- Discovery output is structured and consumable by the Builder.
- Builder creates traceable MOM/SSOT drafts.
- Promotion requires governance and validator gate success.
- Current repository can dogfood at least one construction loop.

# Version v0.6

## Context Activation

Status: Active

Product Goal:

Make constructed context available in the places where humans and agents work.

Primary User Outcome:

At least one operational surface consumes Context OS artifacts without manual
copy-paste.

Included Epic Slices:

- Context Activation Package: read-only working-context package with canonical
  source hashes, mission/goal binding, consumer permissions, provenance,
  freshness, gaps, and invalidation conditions.
- EPIC-008 Runtime CLI: activation command surface.
- Adapter epics: first development-surface integration.
- Validator/Builder integration: activation must consume validated context.

Deferred Capabilities:

- dynamic agent teams
- workflow engine
- multi-surface activation platform
- high-autonomy execution

Definition of Done:

- One activation surface can load governed context.
- Activation is blocked by validator gate failures.
- Users can see which context was activated and from which source artifacts.

# Version v0.7

## Context Health & Learning

Product Goal:

Keep context useful after the first construction.

Primary User Outcome:

A user can see context drift, ownership gaps, stale artifacts, and recommended
maintenance actions.

Included Epic Slices:

- Health Engine and drift detection.
- Validator Engine full-mode signal expansion.
- Knowledge Engine early learning inputs where they support remediation.
- Mission/remediation workflow slices where needed.

Deferred Capabilities:

- full organizational memory substrate
- dynamic agent teams
- autonomous recommendations

Definition of Done:

- Context Health Report is routine and actionable.
- Drift findings produce recommended remediation missions.
- Learning signals can be captured without silently changing SSOT.

---

# Version v0.8

## Organizational Memory

Product Goal:

Make context durable across decisions, changes, and teams.

Primary User Outcome:

A user can retrieve prior decisions, historical rationale, and reusable
context with provenance.

Included Epic Slices:

- EPIC-005 Knowledge Engine: durable Raw Knowledge and interpretation path.
- Context Graph runtime slices required for memory traversal.
- Decision and provenance memory capabilities.

Deferred Capabilities:

- strategic autonomous reasoning
- high-autonomy mission execution

Definition of Done:

- Memory entries are traceable to source artifacts and decisions.
- Prior context can be surfaced during maintenance and construction.
- Memory does not bypass governance or belief-state rules.

---

# Version v0.9

## Contextual Reasoning

Product Goal:

Use governed context to improve recommendations, planning, and execution.

Primary User Outcome:

A user can ask Context OS for context-aware recommendations and receive
answers grounded in SSOT, memory, and governance constraints.

Included Epic Slices:

- Context reasoning.
- Capability registry and governed agent-team assembly.
- Recommendation provenance and authority controls.
- Mission execution slices under explicit human-agent authority.

Deferred Capabilities:

- unrestricted autonomy
- self-modifying governance
- unbounded external execution

Definition of Done:

- Recommendations cite context sources and authority limits.
- Agentic execution remains auditable and governed.
- Reasoning improves decisions without replacing human accountability.

---

# Version v1.0

## Organizational Context Runtime

Product Goal:

Coordinate humans, agents, and systems through a shared contextual model.

Primary User Outcome:

Context becomes operational infrastructure: assess, bootstrap, construct,
activate, learn, and reason operate as one governed runtime loop.

Included Epic Slices:

- All production-critical slices from the Runtime, Discovery, Knowledge,
  Builder, Validator, CLI, Graph, Activation, Agent, Governance, and Memory
  systems.

Deferred Capabilities:

- experimental autonomy beyond approved authority levels
- organization-specific integrations not required for the core runtime

Definition of Done:

- The full product journey is usable end-to-end.
- Context OS dogfoods its own runtime for roadmap, governance, validation,
  assessment, construction, and learning.
- Runtime behavior is auditable, governable, and extensible.
