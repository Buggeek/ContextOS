# 5.5 — Context OS Runtime Maturity Model

Version: 2.0
Last Updated: 2026-09-06
Owner: Context OS Maintainers
Status: Canonical maturity interpretation

## Current decision

Runtime capability maturity, organizational adoption and evidence of value
must be assessed separately. A software version cannot assign an organization
an operating maturity or an autonomy grant.

**v1.0 = L5 Organizational Intelligence is not a defensible current claim.**
v1.0 proved a released local, human-operated Runtime composition, including
self-hosted evolution and a 23/23 integrated benchmark. The old L4/L5 criteria
also demand dynamic teams, sustained adaptive operation, self-instrumentation
and measurable organizational outcomes that this release did not demonstrate.
The release remains valid; the automatic equivalence is retired.

## Three separate assessments

| Assessment | Record | Current evidence |
|---|---|---|
| Runtime capability | Per-capability implementation, public/API surface, tested boundaries and external exercise | Released local engines; seven CLI commands; additional advanced Python APIs; several architectural layers remain unimplemented |
| Adoption repeatability | Named user, organization shape, source scope, setup/operation/recovery tasks and degree of maintainer assistance | Maintainer self-hosting and one assisted repository-local Technology reference; design-partner alpha, not demonstrated self-service |
| Outcome evidence | Correctness, governance, context quality, cognitive burden, execution and user/business outcomes independently | Correctness/governance proof and bounded context-quality evidence; causal time/burden/business improvements unproven |

Use the [Product Reality Matrix](../../SSOT/E.4_Mission_POST-V1-PRODUCT-REALITY-AND-ROADMAP-REBASELINE-001_Product_Reality_Rebaseline.md#product-reality-matrix)
for capability classifications, the [Adoption Playbook](../4.x_adoption/4.0_COS_Adoption_Playbook.md)
for path and prerequisites, and the [value-proof framework](5.6_COS_Current_Product_Definition.md#value-proof-framework)
for evidence requirements. Do not collapse the assessments into a minimum,
maximum or aggregate level. Unknown evidence stays unknown.

Autonomy levels in the Human-Agent Authority Model remain separate,
capability-specific grants. No change here grants or removes authority. High
autonomy is not a prerequisite for valuable adoption.

## Evaluation procedure for current claims

1. Name the capability/use case, target scope, operator and exact evidence basis.
2. Record implemented versus specified behavior and normal versus API-only use.
3. Observe setup, use and recovery; explicitly record procedural assistance.
4. Record outcome measurements and missing baselines without causal inference.
5. Have accountable humans accept the bounded claim and its next evidence gate.

Reassess on material capability/adoption evidence changes, not automatically on
release numbers. Readiness R0-R5 answers scoped context availability/gaps; it
is neither a product adoption certification nor a conversion to organizational
maturity. A healthy command or complete MOM is not organizational value proof.

## Historical model (superseded for current scoring)

The original five dimensions, level definitions, version-to-level table and
promotion procedure below are retained as historical design hypotheses. They
must not be used to assign a current organization, release, installation or
adoption engagement a level. Their universal anchoring and R-to-L conversion
are superseded by the separate assessments above. This preserves the record
without weakening or retroactively expanding what v1.0 actually demonstrated.

## Purpose

This document defines the **Runtime Maturity Model** for Context OS.

Maturity is the canonical way to describe **how operational a Context OS
Runtime instance is** along five dimensions. Every Runtime instance, every
roadmap version, and every adoption engagement is anchored to a Maturity
Level.

This artifact supersedes the inline 5-level scale previously summarized in
[`5.3_COS_Runtime_Strategy.md`](5.3_COS_Runtime_Strategy.md).

Maturity is interpreted through the
[`Theory of the AI-Native Organization`](../0.x_foundations/0.9_COS_Theory_of_the_AI_Native_Organization.md).
An organization does not become AI-native merely by adding agents or raising
autonomy. Direction, context, memory, authority, evidence, learning, and
governed evolution must mature coherently.

---

## Dimensions

A Runtime is measured along five orthogonal dimensions:

| # | Dimension | What it measures |
|---|---|---|
| D1 | Organizational | How explicit and stable the organizational context is |
| D2 | Runtime | How operational the Runtime components are |
| D3 | Governance | How enforced contextual integrity is |
| D4 | Activation | How effectively context reaches humans, agents, systems |
| D5 | Autonomy | How much agentic action is delegated under accountability |

Each dimension has 5 levels. A Runtime's **overall level** is the **minimum**
of its dimension levels — coherence wins over local advancement.

---

## Levels

### Level 1 — Manual

Context is mostly implicit. Artifacts are produced by hand. Validation is
ad-hoc. No agents are operational.

| Dim | Indicator |
|---|---|
| D1 Organizational | Vision and constraints are declared but possibly informal |
| D2 Runtime | No Runtime services running; SSOT exists as files |
| D3 Governance | Reviews happen but are not codified |
| D4 Activation | Humans read SSOT directly; no IDE/agent surface integration |
| D5 Autonomy | Agents at L0–L1 only |

**Promotion gate to Level 2:** MOM complete, governance roster declared, at
least one Runtime component installed.

---

### Level 2 — Assisted

Runtime components are installed. Agents propose; humans approve. Validation
is automated for taxonomy and links.

| Dim | Indicator |
|---|---|
| D1 Organizational | MOM complete; Hypothesis vs Verified tagging applied |
| D2 Runtime | Assessment, validation, bootstrap, and construction components active in `assist` mode |
| D3 Governance | DoR/DoD enforced on every change; Accountability Ledger live |
| D4 Activation | At least one Activation surface (IDE or CLI) actively used |
| D5 Autonomy | Agents at L2 on draft surfaces; L1 elsewhere |

**Promotion gate to Level 3:** drift detection running, mission lifecycle in
routine use.

---

### Level 3 — Managed

Continuous maintenance is in place. Drift is detected and remediated.
Missions run through the Mission Lifecycle end-to-end.

| Dim | Indicator |
|---|---|
| D1 Organizational | Verified context dominates; Hypotheses are tracked and burned down |
| D2 Runtime | Context Health, drift detection, and governed construction loops run routinely |
| D3 Governance | Governance Lifecycle event-driven; audit trail queryable |
| D4 Activation | Multiple Activation surfaces; memory and prior-art signals support routine work |
| D5 Autonomy | Execution Agent at L3 on draft surfaces; promotion criteria documented |

**Promotion gate to Level 4:** Dynamic Team Assembly operating routinely; at
least one capability promoted to L4 with full ledger trail.

---

### Level 4 — Adaptive

Dynamic agent teams operate against evolving context. Capability pools and
team assembly are routine. The organization measurably benefits from agent
leverage while preserving accountability.

| Dim | Indicator |
|---|---|
| D1 Organizational | Strategy adapts using validated learnings within a documented cadence |
| D2 Runtime | Runtime supports mission-scoped orchestration at scale |
| D3 Governance | Policy inheritance enforced; violations auto-route to Governance Lifecycle |
| D4 Activation | Activation Layer serves both IDE and workflow targets |
| D5 Autonomy | Selected capabilities at L4; L5 considered only under explicit governance review |

**Promotion gate to Level 5:** sustained Level 4 with no contextual integrity
regressions across two consecutive evaluation periods.

---

### Level 5 — Organizational Intelligence

Context is operational infrastructure. Humans and intelligent systems
collaborate through a shared contextual model. The Runtime adapts itself
within governance.

| Dim | Indicator |
|---|---|
| D1 Organizational | Strategy, product, and operations co-evolve through measurable context loops |
| D2 Runtime | Self-instrumented; provides decision support to leadership |
| D3 Governance | Governance is itself adaptive within hard policy bounds |
| D4 Activation | Activation reaches humans, agents, and systems uniformly |
| D5 Autonomy | Limited L5 capabilities permitted under continuous audit |

## Readiness vs Maturity

The Context Readiness Assessment introduced in v0.3 reports readiness levels
R0-R5 as defined in
[`1.5.6 Context Readiness Assessment Contract`](../1.x_architecture/1.5_runtime_contracts/1.5.6_Context_Readiness_Assessment_Contract.md).

Readiness answers whether a repository has enough visible context, structure,
governance, and runtime rails to proceed to the next product step. Maturity
answers how operational a Context OS Runtime instance is over time.

Readiness can indicate entry into maturity, but it does not replace the
Runtime Maturity Model:

| Readiness level | Maturity implication |
|---|---|
| R0-R1 | Below L1 evidence quality |
| R2 | L1 evidence can be inventoried |
| R3 | Candidate for v0.4 Guided Bootstrap and L2 entry |
| R4 | Candidate for v0.5 Context Construction under L2 |
| R5 | Strong local precondition for later activation and learning slices |

---

## Evaluation Procedure

Maturity evaluation is a Governance Lifecycle event.

1. Context Guardian compiles current indicators per dimension.
2. Each indicator is scored against the table above.
3. The overall level is the minimum dimension level.
4. Result is recorded as a Decision Record in SSOT.
5. Promotion or regression triggers the relevant lifecycle action.

Evaluation cadence: per release minimum; on-demand on request of Maintainer or
Runtime Owner.

---

## Anti-Patterns

- Reporting maturity as the maximum dimension level (false advancement).
- Skipping promotion gates.
- Granting L4/L5 autonomy without sustaining Level 3 maturity.
- Treating maturity as a marketing claim rather than an operational measure.
