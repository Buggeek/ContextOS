# 0.6 — Context Graph

The Context Graph is a derived representation of the organizational context.

It does not replace documentation, decision-making, or human judgment.  
It makes context **explicit, navigable, and governable** for humans and agents operating inside the same system.

The Context Graph exists to reduce ambiguity and align reasoning — not to create a perfect model of reality.

---

## Purpose of the Context Graph

As organizations grow, context fragments:

- Knowledge lives in documents, tools, repositories, and people.
- Decisions depend on who remembers what.
- Agents amplify whatever context they are given — coherent or not.

The Context Graph exists to:
- expose what the system believes to be true,
- show how concepts relate to each other,
- and constrain reasoning within shared boundaries.

It is not an intelligence layer.  
It is a **contextual boundary layer**.

---

## The Context Graph as an Emergent Structure

The Context Graph is never designed upfront.

It **emerges** from the execution of Context Construction Loops.

The relationship is explicit:

Context Construction Loops  
→ Minimum Operational Map (MOM)  
→ Contextual Entities  
→ Relationships  
→ Context Graph

The graph is therefore:
- derived, not authoritative,
- descriptive, not prescriptive,
- and always secondary to the MOM documents.

If the loops stop running, the graph becomes stale.

---

## Node Types (Contextual Primitives)

The Context Graph uses a minimal and stable set of node types aligned with organizational language.

### System
Represents technical or operational systems:
- services
- platforms
- infrastructure components

This is not a deployment graph. It reflects conceptual systems.

---

### Product / Capability
Represents what the organization delivers:
- products
- features
- internal capabilities
- services

Capabilities exist regardless of implementation details.

---

### Data Entity
Represents meaningful business data concepts:
- customer
- order
- session
- measurement

These are not tables or schemas. They are semantic entities.

---

### Policy / Constraint
Represents explicit rules and limits:
- non-negotiables
- compliance rules
- decision boundaries

Policies constrain both humans and agents.

---

### Context Artifact
Represents MOM documents that describe or govern the system:
- vision
- system maps
- definitions of ready/done

Artifacts are first-class context objects.

---

## Relationship Types (Semantic Links)

The Context Graph intentionally uses a small set of relationships.

### `depends_on`
Indicates reliance between entities:
- a product depends on a system
- a system depends on a data entity

---

### `constrains`
Indicates limitation or boundary:
- a policy constrains a capability
- a rule constrains a process

---

### `governs`
Indicates authority or control:
- a document governs a system
- a policy governs behavior

---

### `produces`
Indicates output:
- a system produces data
- a capability produces outcomes

---

### `describes`
Indicates representation:
- a document describes a system
- a model describes an entity

Relationships are semantic, not technical.  
If a relationship is unclear to humans, it does not belong in the graph.

---

## How the Context Graph Is Built

The Context Graph is constructed only as an **output** of a Context Construction Loop.

It can be built through:
- repository analysis,
- document parsing,
- guided human input,
- or operational signals.

It is never edited manually as a source of truth.

The MOM remains the primary authority.  
The graph reflects the MOM.

---

## Hypothesis vs Verified Context

Every node and relationship in the Context Graph carries a status:

- **Hypothesis** — inferred, assumed, or designed
- **Verified** — confirmed through observation or operation

This distinction is critical.

Agents must know:
- what is believed,
- what is known,
- and what is uncertain.

The Context Graph does not eliminate uncertainty.  
It makes it explicit.

---

## How Agents Use the Context Graph

Agents do not reason *with* the graph.  
They reason **within the constraints it defines**.

The graph allows agents to:
- navigate relevant context,
- avoid invalid assumptions,
- and respect organizational boundaries.

The Context Graph limits agent behavior as much as it enables it.

---

## Human Interaction with the Context Graph

For humans, the Context Graph:
- reduces reliance on memory,
- improves shared understanding,
- and supports collective decision-making.

It enables better conversations, not automatic decisions.

Humans remain accountable.  
Agents remain assistants.

---

## Evolution Path of the Context Graph

The Context Graph evolves incrementally:

- **v0** — explicit index of entities and relationships
- **v1** — navigable graph representation
- **v2** — agent-consumable context layer
- **v3** — contextual reasoning substrate

Each stage is optional and reversible.

No technical implementation is implied by this document.

---

## Design Constraints and Anti-Patterns

The Context Graph must not become:
- an academic ontology,
- a complete mirror of reality,
- or a database optimized for exhaustiveness.

If the graph grows faster than understanding, it is broken.

Context must remain:
- minimal,
- operational,
- and continuously validated.

---

## Summary

The Context Graph is not the goal of Context OS.

It is a **consequence** of operating with explicit context.

When context is constructed correctly,  
the graph emerges naturally.

When the graph exists without living context,  
it becomes fiction.

Context OS prioritizes reality over representation.
