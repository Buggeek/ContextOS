## Purpose

This document is the architectural birth certificate of Context OS.

It defines Context OS from first principles, after the framework, runtime
contracts, roadmap, validator, readiness assessment, guided bootstrap slices,
agent model, governance model, and dogfooding strategy converged into a single
system.

This document does not replace the architecture, roadmap, contracts, SSOT, or
runtime components. It anchors them. When future work asks "what is Context
OS?", this document is the first answer.

---

## Canonical Answer

Context OS is the Organizational Context Runtime: a governed operating system
for organizational context, memory, decisions, capabilities, and human-agent
execution.

Its purpose is to make organizational context operational.

Context OS exists because every organization already runs on context:
purpose, assumptions, decisions, evidence, relationships, constraints,
processes, tools, culture, and memory. Most organizations leave that context
implicit. Context OS makes it explicit, governed, executable, and evolvable.

Context OS is not a documentation framework. Documentation is one storage
surface.

Context OS is not an agent framework. Agents are one activation surface.

Context OS is not a project management method. Missions are one execution
surface.

The underlying model is simpler:

> Organizations evolve by turning intent into work, work into evidence,
> evidence into memory, and memory into better intent under governance.

Context OS is the runtime for that loop.

GENESIS is the first-principles definition of Context OS: what the system is,

[`0.9 Theory of the AI-Native Organization`](0.9_COS_Theory_of_the_AI_Native_Organization.md)

The relationship is:

```text
GENESIS -> first principles of Context OS
Theory -> organizational model and falsifiable claims
Architecture -> system structure
Runtime -> operational capabilities
Roadmap -> evidence-sequenced delivery
```

The Theory sits above product and Runtime interpretation but below no new
authority. It cannot relax GENESIS, governance, or released product decisions.

## First Principles

Context OS rests on nine first principles.

| Principle | Meaning |
|---|---|
| Context is infrastructure | Shared understanding is an operating dependency, not a documentation byproduct |
| Intent precedes execution | Work without explicit intent creates local optimization and drift |
| Evidence promotes belief | Claims become trusted only through observable evidence and decisions |
| Memory is governed context over time | Organizational memory is not storage; it is retained, versioned, accountable context |
| Governance is the control plane | Context mutation, authority, activation, and memory promotion require explicit rules |
| Humans own accountability | Agents can suggest, draft, execute, and verify, but humans own consequential decisions |
| Agents require bounded context | Agent quality depends on explicit constraints, authority, inputs, and success criteria |
| Tools are side-effect surfaces | Tool access is not intelligence and must be permissioned separately |
| Evolution is continuous | Context decays unless observation, validation, learning, and re-anchoring are routine |

## Organizational Evolution Model

The canonical organization in Context OS is not modeled as a hierarchy. It is
modeled as an evolving system of intent, value, operation, evidence, memory,
and governance.

### Organizational Primitives

| Primitive | Definition | Primary question |
|---|---|---|
| Organizational Intent | The declared reason for coordinated action | Why are we acting? |
| Purpose | The enduring reason the organization exists | Why should this organization exist? |
| True North | The highest-order direction used to resolve tradeoffs | What must remain directionally true? |
| Customer Promise | The value commitment made to customers or beneficiaries | What do we promise to make better? |
| Value Model | The mechanism by which the organization creates, delivers, and captures value | How does value move? |
| Strategic Outcomes | Measurable outcomes that translate intent into targets | What should change in reality? |
| Principles | Non-negotiable constraints for action | What must not be violated? |
| Cultural Codes | Behavioral norms that shape judgment under uncertainty | How do we behave when rules are incomplete? |
| Decision Principles | Rules for selecting between valid alternatives | How do we decide? |
| Customer Journey | The lived path through which value is experienced | Where does the customer encounter value or friction? |
| Value Streams | Recurring flows that create and deliver value | How is value produced operationally? |
| Operations | Stable domains of recurring work | What functions must run repeatedly? |
| Capabilities | Domains of ability required to perform operations | What must we be able to do? |
| Missions | Bounded units of accountable change | What specific change are we executing now? |
| Work | Concrete actions taken by humans, agents, or systems | What was done? |
| Evidence | Observable proof produced or discovered by work | What do we know because of this? |
| Knowledge | Interpreted evidence with provenance and confidence | What does the evidence mean? |
| Memory | Retained knowledge, decisions, and belief states over time | What must be remembered? |
| Context | The active frame used for interpretation and action | What should actors know before acting? |
| Governance | Rules, authority, ownership, and auditability for change | Who may change what, under what evidence? |
| Learning | Generalization from evidence into reusable context | What should change in how we operate? |
| Evolution | Governed change to intent, systems, operations, and memory | How does the organization become more fit? |

### Primitive Relationships

Purpose defines why the organization exists.

True North converts purpose into direction.

Customer Promise externalizes that direction as value.

Value Model explains how the promise is fulfilled and sustained.

Strategic Outcomes make the value model measurable.

Principles, Cultural Codes, and Decision Principles constrain how outcomes may
be pursued.

Customer Journey exposes where value is experienced.

Value Streams organize how value is delivered.

Operations run those streams.

Capabilities make operations possible.

Missions temporarily assemble capabilities to change the organization.

Work performs the mission.

Evidence proves what happened.

Knowledge interprets evidence.

Memory retains knowledge and decisions over time.

Context activates relevant memory for current action.

Governance controls mutation, authority, and promotion.

Learning converts repeated evidence into improved models.

Evolution updates intent, operations, capabilities, and governance when the
evidence requires it.

This is the universal organizational model. Technology is only one operation
inside it.

## Organizational Runtime Model

The Runtime is the operational layer that keeps the Organizational Evolution
Model alive.

It is not one engine. It is a set of engines with different maturity profiles.

### Foundational Runtime Components

Foundational components are required before higher-order runtime behavior is
safe.

| Component | Role | Dependency position |
|---|---|---|
| Runtime CLI | Human and automation entry surface | Wraps engines; must not duplicate engine logic |
| Validator Engine | Deterministic integrity gate | Protects structure, taxonomy, links, governance, ownership, and drift |
| Context Readiness Engine | First assessment surface | Uses inventory and validation to answer what exists, what is missing, and what to do next |
| Guided Bootstrap Engine | Read-only then governed setup planning | Converts readiness into proposed setup actions before any writes |
| Governance Layer | Authority, policy, ownership, and audit control | Surrounds all runtime actions |

### Construction Runtime Components

Construction components turn sources into governed context.

| Component | Role | Dependency position |
|---|---|---|
| Discovery Engine | Observes structured sources and maps what exists | Precedes Builder; feeds Readiness, Health, and Graph |
| Knowledge Engine | Interprets unstructured knowledge with provenance | Follows clear source paths; feeds Builder and Memory |
| Context Builder | Produces MOM and SSOT drafts from inputs | Requires Discovery, Knowledge, templates, governance, and Validator gates |

### Memory and Reasoning Components

Memory and reasoning components increase leverage after construction is
governed.

| Component | Role | Dependency position |
|---|---|---|
| Context Memory | Retains belief states, versions, decisions, and historical context | Requires governance and evidence discipline |
| Context Graph | Derives navigable relationships from SSOT, memory, evidence, and missions | Derived index; never authoritative |
| Context Health Engine | Detects drift, stale context, ownership gaps, and learning opportunities | Requires Validator, Discovery, and memory signals |
| Reasoning Layer | Produces recommendations grounded in SSOT, memory, graph, and authority | Requires mature context and governance |

### Activation Runtime Components

Activation components deliver context into real work.

| Component | Role | Dependency position |
|---|---|---|
| Activation Layer | Delivers governed context into tools, workflows, IDEs, and agent surfaces | Requires validated context and declared authority |
| Human-Agent Runtime | Coordinates humans and agents through roles, missions, skills, tools, and authority | Requires Mission Packets, governance, and activation |
| Mission Runtime | Manages mission lifecycle, evidence, events, and closure | Requires authority model, validator gates, and memory capture |

### Engine Dependency Rule

Context OS must not activate a higher-order engine to compensate for an
immature lower-order engine.

For example:

- The Knowledge Engine must not invent context that Discovery cannot ground.
- The Context Builder must not promote artifacts that Governance cannot own.
- The Context Graph must not become source of truth when SSOT is weak.
- The Human-Agent Runtime must not increase autonomy when Mission Packets are
  incomplete.

## Human-Agent Organization Model

Context OS treats humans, agents, capabilities, skills, tools, and operations
as separate concepts.

### Human Role

Humans provide:

- intent
- accountability
- strategic judgment
- authority grants
- approval of consequential change
- governance decisions
- interpretation of ambiguous tradeoffs

Humans are not emergency fallbacks. They are the accountable governors of the
system.

### Agent Role

Agents provide:

- analysis
- synthesis
- planning
- drafting
- execution within bounds
- verification
- monitoring
- recommendation

Agents do not own accountability. They operate under authority.

### Capability Role

Capabilities describe what the organization can do. They are domain-level
abilities such as strategy, product, technology, marketing, sales, finance,
legal, people, operations, research, data, and customer success.

Capabilities can be staffed by humans, agents, or both.

### Skill Role

Skills are reusable procedures or cognitive abilities that a role can use.
Examples include analysis, validation, synthesis, estimation, facilitation,
research, code modification, financial modeling, or incident triage.

Skills do not decide. They enable roles.

### Tool Role

Tools are permissioned side-effect surfaces: repositories, databases,
ticketing systems, CRMs, analytics tools, design tools, communication systems,
cloud consoles, or local files.

Tool access must be narrower than capability. A capable actor is not
automatically allowed to act in every tool.

### Authority Flow

Authority flows downward:

```text
Doctrine -> Organizational Policy -> Project Policy -> Mission Policy -> Action
```

Every layer may constrain the layer below. No layer may silently relax the
layer above.

Delegation is expressed through autonomy levels:

```text
L0 none
L1 suggest
L2 draft
L3 execute with approval
L4 execute autonomously within bounds
L5 self-improve within governance
```

The default for new capabilities is L1. Promotion requires evidence.

## Organizational Evolution Loop

The current loop hypothesis is close, but it mixes different levels of
abstraction. The canonical loop should be:

```text
Anchor -> Observe -> Interpret -> Assess -> Propose -> Decide -> Apply -> Validate -> Activate -> Measure -> Learn -> Re-anchor
```

### Loop Semantics

| Step | Meaning |
|---|---|
| Anchor | Declare intent, purpose, constraints, and success criteria |
| Observe | Inspect reality through repositories, systems, conversations, metrics, and feedback |
| Interpret | Convert observations into claims with provenance and belief states |
| Assess | Compare current context against desired operating state |
| Propose | Generate options, bootstrap plans, drafts, remediations, or mission plans |
| Decide | Human-accountable decision under governance |
| Apply | Execute approved change within authority bounds |
| Validate | Verify structure, outcomes, evidence, and policy compliance |
| Activate | Make validated context available to humans, agents, tools, and workflows |
| Measure | Compare outcomes against strategic and mission criteria |
| Learn | Promote reusable lessons into memory, policy, roles, or capabilities |
| Re-anchor | Update intent, roadmap, principles, or operating model when evidence demands it |

This loop generalizes the product journey:

```text
Assess -> Bootstrap -> Construct -> Activate -> Learn -> Reason
```

The product journey is how users adopt the runtime. The evolution loop is how
organizations operate once the runtime exists.

## Self-Hosting Model

Context OS must become increasingly capable of building Context OS.

Self-hosting is not a vanity goal. It is the primary proof that the runtime is
coherent.

### Self-Hosting Loop

```text
Roadmap intent -> Mission Packet -> Runtime execution -> Evidence -> Validator
gate -> Readiness/Health assessment -> Memory capture -> Roadmap evolution
```

Every release should improve at least one of these capabilities:

1. The repository can explain more of its own context.
2. The runtime can assess more of its own readiness or health.
3. The CLI can expose more governed runtime behavior.
4. Mission Packets can carry more of the required execution context.
5. Validator rules can protect more of the architecture.
6. Bootstrap and Builder outputs can reduce manual structure work.
7. Evidence from release work can update SSOT and roadmap with less prompt
   text.

The long-term target is that a maintainer can initiate a release with a short
goal because the Mission Packet, SSOT, runtime reports, and memory carry the
context currently embedded in long prompts.

## Universal Execution Model

The proposed execution chain is directionally correct:

```text
Roadmap -> Release -> Goal -> Mission Packet -> Slices -> Execution -> Evidence -> Audit -> Knowledge Capture -> Roadmap Evolution
```

The canonical version is:

```text
Intent -> Roadmap Thesis -> Release Goal -> Mission Packet -> Slice Plan -> Execution -> Verification Evidence -> Governance Decision -> Memory Capture -> Roadmap Rebase
```

### Execution Entities

| Entity | Meaning |
|---|---|
| Intent | Why this body of work matters |
| Roadmap Thesis | The strategic bet encoded in the roadmap |
| Release Goal | User-visible outcome for a version |
| Mission Packet | Bounded accountable execution contract |
| Slice Plan | Smallest coherent implementation or documentation unit |
| Execution | Work performed by humans and agents |
| Verification Evidence | Tests, reports, diffs, assessments, reviews, and observed outcomes |
| Governance Decision | Approval, rejection, escalation, or deferral |
| Memory Capture | Lessons, decisions, belief-state changes, and reusable context |
| Roadmap Rebase | Adjustment of future work based on evidence |

Work that cannot be tied to this chain is not operationally legible in
Context OS.

## Universal Organization Model

Context OS must apply beyond technology. Technology is one operation inside
the organization, not the shape of the whole model.

Every operation can be modeled through the same runtime contract:

```text
Intent -> Value Stream -> Capabilities -> Missions -> Work -> Evidence -> Memory -> Governance -> Evolution
```

### Operation Mapping

| Operation | Example context artifacts | Example evidence |
|---|---|---|
| Strategy | True North, strategic outcomes, decision principles | board decisions, market signals, strategic metrics |
| Product | product map, roadmap, hypotheses, customer journey | experiments, usage, discovery notes |
| Technology | system map, data entities, service catalog, ADRs | tests, incidents, architecture diffs |
| Marketing | positioning, campaigns, segments, channels | conversion, reach, attribution, brand signals |
| Sales | pipeline model, ICP, qualification criteria | win/loss data, deal notes, forecast accuracy |
| Customer Success | onboarding journey, health model, escalation paths | retention, support tickets, customer outcomes |
| Finance | value model, budget, unit economics, controls | revenue, margin, runway, audit records |
| Legal | policy, obligations, risk register, approvals | contracts, compliance checks, legal decisions |
| People | roles, culture codes, hiring needs, performance loops | headcount, retention, capability gaps |
| Operations | process maps, SLAs, vendor dependencies | throughput, incidents, process metrics |
| Research | questions, protocols, evidence inventory | studies, findings, confidence levels |
| Data | metric definitions, lineage, governance, dashboards | data quality, metric drift, decision support |

Each operation can have different artifacts and tools, but the runtime model
is the same.

## Lineage Convergence

Several initiatives contributed conceptual DNA to Context OS. They are not
separate products in the canonical architecture.

| Initiative | Converged role inside Context OS |
|---|---|
| Knowledge Mapper | Discovery Engine: source inventory, system mapping, ownership mapping, relationship mapping |
| Memor.IA | Context Memory: belief states, versioned memory, temporal context, retention, organizational memory |
| Cocora | Knowledge Engine, Activation Layer, and Human-Agent Runtime: interpretation, interaction, agent-facing context delivery |
| Lukspeed | Operational laboratory: pressure-testing readiness, bootstrap, construction, activation, learning, and real work loops |

The convergence rule is:

> External initiative concepts may survive only as Context OS capabilities,
> engines, operating patterns, or examples. They must not create parallel
> architecture.

The current positioning, "Organizational Context Runtime", remains correct as
the product category.

It is strong because it says:

- organizational, not merely technical
- context, not generic knowledge
- runtime, not static documentation

The stronger full positioning is:

> Context OS is the Organizational Context Runtime that makes context, memory,

The shortest positioning remains:

> Context OS makes organizational context operational.

"Operating system for organizational evolution" is a useful explanatory
phrase, but it should not replace "Organizational Context Runtime" as the

## Execution Impact For Agents

Codex, Claude Code, and future agents should interact with Context OS through
Mission Packets, not long unstructured prompts.

### Current State

Prompts carry too much:

- objective
- context
- constraints
- authority
- acceptance criteria
- known state
- test commands
- output format
- governance requirements

This is workable during early construction. It is not the target runtime.

### Target State

Mission Packets carry:

- intent
- owner
- scope in and out
- context references
- constraints
- success criteria
- evidence plan
- authority grants
- required outputs
- lifecycle state

Agents consume the packet, consult runtime reports, execute bounded work,
produce evidence, and update memory through governance.

Prompt text should shrink to:

```text
Run mission <id>.
```

or:

```text
Assess mission <id> and propose the next slice.
```

The runtime should provide the context that prompts currently repeat.

## Non-Negotiable Constraints

- SSOT is authoritative.
- Context Graph is derived.
- Memory promotion requires evidence.
- Governance surrounds every context mutation.
- Human accountability cannot be delegated away.
- Agents operate only under explicit authority.
- Tools require separate permission from capability.
- Read-only assessment and planning must precede writes.
- Bootstrap must never invent verified truth.
- Activation must be blocked by failed gates.
- Self-hosting must improve release by release.

## Final Definition

Context OS is the Organizational Context Runtime for organizational evolution.

It turns intent into governed work, work into evidence, evidence into memory,
and memory into better coordinated action across humans, agents, tools, and
systems.

Its canonical journey is:

```text
Assess -> Bootstrap -> Construct -> Activate -> Learn -> Reason
```

Its canonical operating loop is:

```text
Anchor -> Observe -> Interpret -> Assess -> Propose -> Decide -> Apply -> Validate -> Activate -> Measure -> Learn -> Re-anchor
```

Its canonical execution unit is the Mission Packet.

Its canonical control plane is governance.

Its canonical asset is context.

Its canonical proof is self-hosting.

The organizational outcome is defined by the
[`Theory of the AI-Native Organization`](0.9_COS_Theory_of_the_AI_Native_Organization.md):
Context OS enables organizations to combine human and machine intelligence and
govern their own evolution without silently rewriting organizational truth.
