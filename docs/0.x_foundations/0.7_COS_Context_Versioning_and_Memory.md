# 0.7 — Context Versioning and Memory

## Purpose

Context OS treats organizational context as a **living artifact**. Context is
not static documentation; it is a stream of beliefs, decisions, and
verifications that must be **versioned**, **scoped**, and **remembered**.

This document defines the foundational model for:

- How truth claims preserve independent epistemic, governance, and strategic
  states.
- How context is partitioned into **memory tiers**.
- How context is **versioned** over time.
- How **retention** decisions are made.

It anchors the runtime concepts of Context Graph
([`0.6`](0.6_COS_Context_Graph.md)), Construction Loops
([`0.5`](0.5_COS_Context_Construction_Loops.md)), and Validator drift
detection ([`1.5.1`](../1.x_architecture/1.5_runtime_contracts/1.5.1_Validator_Contract.md)).

---

## 1. Truth Axes

Every claim recorded in Context OS preserves three independent axes. The
earlier single `belief_state` model is superseded by this canonical model.

| Axis | States | Meaning |
|---|---|---|
| Epistemic support | `observed`, `declared`, `inferred`, `derived`, `unknown` | How the assertion is supported |
| Governance lifecycle | `suggested`, `draft`, `reviewed`, `approved`, `canonical` | What organizational authority the artifact has received |
| Strategic belief | `hypothesis`, `verified`, `deprecated` | How the organization currently treats a strategic claim |

The axes must not be collapsed. Observed evidence may remain non-canonical; a
canonical artifact may contain an explicit hypothesis; a deprecated claim may
remain preserved as historical memory.

Existing v0.x Runtime schemas that expose a field named `belief_state` use it
as a compatibility alias for epistemic support only. They do not collapse or
replace governance lifecycle or strategic belief.

Promotion to `verified` requires evidence and a recorded decision. Promotion
to `canonical` additionally requires the governed Context Construction path
(see [`1.5.3`](../1.x_architecture/1.5_runtime_contracts/1.5.3_Context_Graph_Schema.md)).

## 2. Temporal Context

Context has **time**. Three temporal axes are tracked for every artifact and
graph node:

| Axis | Meaning |
|---|---|
| `valid_from` | When the claim started being true |
| `valid_to` | When the claim stopped being true (null = current) |
| `observed_at` | When the runtime last confirmed the claim |

Consequences:

1. Historical queries are first-class. "What did we believe on date X" is
   answerable.
2. Versioning does not delete `deprecated` nodes; it sets `valid_to`. A
   separate governed retention decision is required for any later archival,
   forgetting, minimization, or content removal.
3. Drift detection compares `observed_at` against external system state.

## 3. Memory Tiers

Context OS distinguishes three memory tiers. Each has a different scope,
lifecycle, and authority.

### 3.1 Working Memory

| Property | Value |
|---|---|
| Scope | A single mission or interaction |
| Lifetime | Bounded by mission lifecycle |
| Storage | Mission Packet + ephemeral notes |
| Authority | Mission Owner |
| Persistence | Not promoted to SSOT unless explicitly extracted |

Working memory exists to keep a mission focused. It must not pollute SSOT.

### 3.2 Project Memory

| Property | Value |
|---|---|
| Scope | A project, repository, or product area |
| Lifetime | Project lifecycle |
| Storage | Project SSOT subset + project-scoped graph |
| Authority | Project Owner + Product Owner |
| Persistence | Survives across missions within the project |

Project memory captures patterns, decisions, and verified facts specific to
one project. It is the operational layer most agents read from.

### 3.3 Organizational Memory

| Property | Value |
|---|---|
| Scope | Entire organization |
| Lifetime | Indefinite (with retention rules) |
| Storage | Organization SSOT + organization-wide graph |
| Authority | Maintainers + Governance roster |
| Persistence | Governed; canonical organizational context supersedes lower tiers on conflict |

Organizational memory holds doctrine, vision, principles, governance
policies, cross-project entities, verified strategic decisions, and their
historical lineage. A record does not become authoritative merely because it
is retained at organizational scope.

### Conflict Resolution

When tiers disagree:

```
Canonical organizational context > canonical project context > working context
```

A working memory claim never overrides canonical project context. Project
context never overrides canonical organizational context. Historical or
retrieved memory has no conflict priority of its own. Conflicts must be either
resolved through governance or recorded as drift findings.

## 4. Context Versioning

Every memory tier produces a **versioned context snapshot**.

```yaml
context_version:
  schema: contextos.context.version/1
  id: <ulid>
  tier: working | project | organizational
  produced_at: <iso8601>
  produced_by: <mission id or runtime event>
  parent_version: <ulid or null>
  artifact_set: [<artifact path, hash>...]
  graph_fingerprint: <hash>
  truth_summary:
    epistemic_support: { observed: <int>, declared: <int>, inferred: <int>, derived: <int>, unknown: <int> }
    governance_lifecycle: { suggested: <int>, draft: <int>, reviewed: <int>, approved: <int>, canonical: <int> }
    strategic_belief: { hypothesis: <int>, verified: <int>, deprecated: <int> }
```

Rules:

1. **Append-only.** Versions are never modified after creation.
2. **Linear within tier.** Each version has at most one parent.
3. **Referenced by missions.** Every mission records the
   `context_version` it consulted, so post-hoc analysis is possible.
4. **Citable by decisions.** Every Decision Record cites the
   `context_version` under which it was decided.

## 5. Retention

Context OS preserves the following classes until an explicit governed
retention decision changes their state:

- **All `verified` claims**.
- **All `decisions`**.
- **All `evidence`** linked to verified claims.
- **Deprecated nodes**, with `valid_to` set.

Preservation is not an assertion of permanent retention. Retention duration,
sensitivity, legal hold, expiration, archival, and forgetting require an
explicit Governance policy and accountable authority. Until that policy
exists, the Runtime must not silently delete, compact, expire, or declare any
class permanently retained.

This preservation baseline is conservative, not permanent. The canonical
policy model is defined by the
[`Organizational Memory Retention Governance Contract`](../1.x_architecture/1.5_runtime_contracts/1.5.13_Organizational_Memory_Retention_Governance_Contract.md).

Under a future separately authorized policy implementation, Context OS may
consider compaction of:

- **Working memory** after mission closure (summary retained; raw notes
  may be discarded per policy).
- **Inferred-only nodes** with no inbound `verifies` edge after a
  retention window declared by Governance.

Context OS must not silently drop:

- Hypothesis nodes (must be explicitly killed or verified).
- Authority ledger entries.
- Drift findings.

Context OS also must not silently retain every source forever. Retention state
is independent from truth, authority, sensitivity, access, and strategic
belief. Expiration creates a review candidate, not deletion. Operational
forgetting changes normal use, not necessarily physical preservation.

Destructive or irreversible behavior requires a separate execution contract,
exact human authority, policy resolution, hold checks, validation, evidence,
and an explicit recovery or irreversibility statement.

## 6. Memory Hygiene

The Validator
([`1.5.1`](../1.x_architecture/1.5_runtime_contracts/1.5.1_Validator_Contract.md))
enforces:

- Hypothesis closure within declared windows.
- Ownership coverage at project and organizational tiers.
- Drift between `observed_at` and current external state.
- No working-memory leakage into SSOT without promotion.

The Context Guardian role
(see [`3.6`](../3.x_operation/3.6_COS_Human_Agent_Authority_Model.md)) is
the operational owner of memory hygiene.

---

## 7. Anti-Patterns

- Treating SSOT as a wiki that is edited freely without belief state.
- Deleting deprecated nodes "to keep things clean".
- Promoting a hypothesis to verified without evidence and a decision.
- Letting working memory accumulate into SSOT through informal handoffs.
- Treating organizational memory as a write surface for missions.
