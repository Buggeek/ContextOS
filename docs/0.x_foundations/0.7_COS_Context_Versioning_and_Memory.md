# 0.7 — Context Versioning and Memory

## Purpose

Context OS treats organizational context as a **living artifact**. Context is
not static documentation; it is a stream of beliefs, decisions, and
verifications that must be **versioned**, **scoped**, and **remembered**.

This document defines the foundational model for:

- How beliefs evolve from **hypothesis** to **verified** to **deprecated**.
- How context is partitioned into **memory tiers**.
- How context is **versioned** over time.
- How **retention** decisions are made.

It anchors the runtime concepts of Context Graph
([`0.6`](0.6_COS_Context_Graph.md)), Construction Loops
([`0.5`](0.5_COS_Context_Construction_Loops.md)), and Validator drift
detection ([`1.5.1`](../1.x_architecture/1.5_runtime_contracts/1.5.1_Validator_Contract.md)).

---

## 1. Belief States

Every claim recorded in Context OS — every entity, system fact, product
hypothesis, policy, mission outcome — carries an explicit **belief state**.

| State | Meaning | Origin |
|---|---|---|
| `observed` | Directly read from a connected source | Discovery |
| `inferred` | Derived from interpretation | Knowledge / Builder |
| `hypothesis` | Declared as a bet, not yet validated | Product / Strategy |
| `verified` | Validated by evidence + decision | Verification |
| `deprecated` | Superseded but retained for traceability | Governance |

A claim cannot skip states. Promotion from `hypothesis` → `verified` requires
an `evidence` node and a recorded decision
(see [`1.5.3`](../1.x_architecture/1.5_runtime_contracts/1.5.3_Context_Graph_Schema.md)).

---

## 2. Temporal Context

Context has **time**. Three temporal axes are tracked for every artifact and
graph node:

| Axis | Meaning |
|---|---|
| `valid_from` | When the claim started being true |
| `valid_to` | When the claim stopped being true (null = current) |
| `observed_at` | When the runtime last confirmed the claim |

Consequences:

1. Historical queries are first-class. "What did we believe on date X" is
   answerable.
2. `deprecated` nodes are not deleted; their `valid_to` is set.
3. Drift detection compares `observed_at` against external system state.

## 3. Memory Tiers

Context OS distinguishes three memory tiers. Each has a different scope,
lifecycle, and authority.

### 3.1 Working Memory

| Property | Value |
|---|---|
| Scope | A single mission or interaction |
| Lifetime | Bounded by mission lifecycle |
| Storage | Mission Packet + ephemeral notes |
| Authority | Mission Owner |
| Persistence | Not promoted to SSOT unless explicitly extracted |

Working memory exists to keep a mission focused. It must not pollute SSOT.

### 3.2 Project Memory

| Property | Value |
|---|---|
| Scope | A project, repository, or product area |
| Lifetime | Project lifecycle |
| Storage | Project SSOT subset + project-scoped graph |
| Authority | Project Owner + Product Owner |
| Persistence | Survives across missions within the project |

Project memory captures patterns, decisions, and verified facts specific to
one project. It is the operational layer most agents read from.

### 3.3 Organizational Memory

| Property | Value |
|---|---|
| Scope | Entire organization |
| Lifetime | Indefinite (with retention rules) |
| Storage | Organization SSOT + organization-wide graph |
| Authority | Maintainers + Governance roster |
| Persistence | Authoritative; supersedes lower tiers on conflict |

Organizational memory holds doctrine, vision, principles, governance
policies, cross-project entities, and verified strategic decisions.

### Conflict Resolution

When tiers disagree:

```
Organizational > Project > Working
```

A working memory belief never overrides project memory. A project memory
belief never overrides organizational memory. Conflicts must be either
resolved (promotion or rejection) or recorded as drift findings.

## 4. Context Versioning

Every memory tier produces a **versioned context snapshot**.

```yaml
context_version:
  schema: contextos.context.version/1
  id: <ulid>
  tier: working | project | organizational
  produced_at: <iso8601>
  produced_by: <mission id or runtime event>
  parent_version: <ulid or null>
  artifact_set: [<artifact path, hash>...]
  graph_fingerprint: <hash>
  belief_summary:
    observed: <int>
    inferred: <int>
    hypothesis: <int>
    verified: <int>
    deprecated: <int>
```

Rules:

1. **Append-only.** Versions are never modified after creation.
2. **Linear within tier.** Each version has at most one parent.
3. **Referenced by missions.** Every mission records the
   `context_version` it consulted, so post-hoc analysis is possible.
4. **Citable by decisions.** Every Decision Record cites the
   `context_version` under which it was decided.

---

## 5. Retention

Context OS retains:

- **All `verified` claims** indefinitely.
- **All `decisions`** indefinitely.
- **All `evidence`** linked to verified claims indefinitely.
- **Deprecated nodes** indefinitely, with `valid_to` set.

Context OS may compact:

- **Working memory** after mission closure (summary retained; raw notes
  may be discarded per policy).
- **Inferred-only nodes** with no inbound `verifies` edge after a
  retention window declared by Governance.

Context OS must not silently drop:

- Hypothesis nodes (must be explicitly killed or verified).
- Authority ledger entries.
- Drift findings.

---

## 6. Memory Hygiene

The Validator
([`1.5.1`](../1.x_architecture/1.5_runtime_contracts/1.5.1_Validator_Contract.md))
enforces:

- Hypothesis closure within declared windows.
- Ownership coverage at project and organizational tiers.
- Drift between `observed_at` and current external state.
- No working-memory leakage into SSOT without promotion.

The Context Guardian role
(see [`3.6`](../3.x_operation/3.6_COS_Human_Agent_Authority_Model.md)) is
the operational owner of memory hygiene.

---

## 7. Anti-Patterns

- Treating SSOT as a wiki that is edited freely without belief state.
- Deleting deprecated nodes "to keep things clean".
- Promoting a hypothesis to verified without evidence and a decision.
- Letting working memory accumulate into SSOT through informal handoffs.
- Treating organizational memory as a write surface for missions.
