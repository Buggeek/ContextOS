# 0.5 — Context Construction Loops

Context OS is not a static framework.  
It is a **context construction engine** that operates through repeatable loops.

These loops define **how context is created, validated, evolved, and governed** over time — for humans and agents operating inside the same system.

The goal is not completeness.  
The goal is **coherence under change**.

---

## Why Context Construction Loops exist

In traditional organizations, context is:
- implicit,
- fragmented,
- and reconstructed informally by people.

This works until:
- scale increases,
- systems become distributed,
- or AI agents enter the workflow.

At that point, missing or inconsistent context stops being a soft problem and becomes an operational risk.

Context Construction Loops exist to:
- make context explicit,
- keep it aligned with reality,
- and ensure reasoning (human or agentic) happens under shared constraints.

---

## Loops, not phases

Context OS does not operate in linear phases.

Instead, it runs **loops** that can be executed:
- at different moments,
- in different orders,
- and multiple times over the life of an organization.

Every loop produces or updates artifacts in the **Minimum Operational Map (MOM)**.

---

## Loop 0 — Why Anchor Loop (Bootstrapping)

### Purpose
Establish the foundational intent and constraints that govern all reasoning and decisions.

This loop answers:
- Why does this system exist?
- What outcomes matter?
- What tradeoffs are non-negotiable?

Without this loop, all other loops drift.

### Typical triggers
- New organization or product
- Major strategic reset
- Introduction of agents into decision-making

### Inputs
- Guided human responses (founder, leadership, product owner)
- No prior documentation required

### Outputs (minimum)
- `S.1_Vision`
- `G.1_Definition_of_Ready`
- `G.2_Definition_of_Done`
- Explicit non-negotiable constraints and policies

### Key rule
This loop always runs **first**, even if the output is rough or incomplete.

---

## Loop 1 — Discovery Loop (Brownfield)

### Purpose
Discover and map the **actual system**, not the intended one.

This loop assumes the organization already exists and contains implicit knowledge spread across tools and repositories.

### Typical triggers
- Existing company or product
- Legacy systems
- Multi-repo environments

### Inputs
- Source code repositories
- Documentation (partial or outdated)
- Configuration files
- Schemas, APIs, infrastructure definitions

### Outputs (minimum)
- `A.1_System_Map` (as-is)
- `A.4_Data_Entities` (observed)
- Explicit list of gaps, contradictions, and unknowns

### Key rule
This loop **does not invent** context.  
Everything is marked as:
- Observed
- Inferred
- Unknown

---

## Loop 2 — Guided Construction Loop (Greenfield)

### Purpose
Construct an initial coherent context when little or nothing exists.

This loop co-creates context through guided questioning and structured inference.

### Typical triggers
- Solo founders
- Early-stage startups
- New product initiatives

### Inputs
- Structured interviews
- High-level descriptions
- Hypotheses and assumptions

### Outputs (minimum)
- `S.1_Vision` (hypothesis-based)
- `P.1_Product_Map`
- `A.1_System_Map` (idealized)
- `A.4_Data_Entities` (hypothetical)

### Key rule
All outputs are explicitly tagged as **hypothesis** until validated by reality or Loop 1.

---

## Loop 3 — Operational Drift Control Loop (Always-On)

### Purpose
Prevent context decay as the system evolves.

This loop keeps the Minimum Operational Map aligned with:
- real usage,
- operational signals,
- and product evolution.

### Typical triggers
- Releases
- Incidents
- Support tickets
- New features or services
- Structural changes

### Inputs
- Backlog changes
- Issues and incidents
- Metrics and usage signals
- Architectural changes

### Outputs
- Incremental updates to MOM documents
- Context change logs
- Refined backlog grounded in current reality

### Key rule
No significant operational change happens without a corresponding context update.

---

## Hypothesis vs Verified Context

Context OS explicitly distinguishes between:
- **Hypothesis**: assumed, designed, or inferred context
- **Verified**: confirmed through observation or operation

This distinction:
- prevents false certainty,
- guides validation work,
- and constrains agent reasoning.

Agents must know **what is believed** versus **what is known**.

---

## Human and Agent Roles per Loop

| Loop | Human Role | Agent Role |
|----|----|----|
| Loop 0 | Intent owner | Structure + synthesis |
| Loop 1 | Validator | Discovery + mapping |
| Loop 2 | Co-designer | Guided generation |
| Loop 3 | Arbiter | Monitoring + diff detection |

Agents assist.  
Humans remain accountable.

---

## Metrics of a healthy loop

A loop is considered healthy when:
- context artifacts are small and updated,
- decisions reference explicit context,
- agents require fewer assumptions,
- and drift is detected early.

If context grows faster than understanding, the loop has failed.

---

## Relationship to the Context Graph

Each loop contributes nodes and edges to the **Context Graph**:
- systems,
- products,
- data entities,
- policies,
- and their relationships.

In early versions, the Context Graph may exist as a simple index.  
Over time, it becomes a navigable, queryable map.

The graph is a consequence of the loops — not a prerequisite.

---

## Design principle

Context OS optimizes for:
- minimum viable context,
- continuous evolution,
- and shared reasoning constraints.

If context becomes heavy, static, or ceremonial, the system is broken.

Context must remain **operational**.

---

## Summary

Context Construction Loops define:
- how context enters the system,
- how it is validated,
- and how it stays alive.

They are the execution model of Context OS.

Without them, Context OS is documentation.  
With them, it becomes an operating system.
