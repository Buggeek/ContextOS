# 1.5.10 - Context Health Report Contract
## Version: 0.3.0
Last Updated: 2026-08-20
Owner: Context OS Maintainers
Status: active

---

## Purpose

Define the minimum read-only contract for determining whether organizational
context is trustworthy, useful in real work, and producing governed learning.

The report answers:

```text
What is unhealthy, what remains unknown, what are we learning, and what should
the organization consider updating?
```

---

## Schema

```text
contextos.health.report/1
```

Structured Mission-use evidence consumed by Health uses:

```text
contextos.mission.context_use_evidence/1
```

---

## Position In The Evolution Loop

```text
Context
-> Activation
-> Execution
-> Evidence
-> Measurement
-> Learning
-> Context Update Candidate
-> Governance
-> Existing Context Construction Lifecycle
-> Re-anchor
```

The Health Report observes and recommends. It does not mutate context.

---

## Health Dimensions

The initial report contains three views in one engine and one report. They are
not separate engines.

| Dimension | Question | Example evidence |
|---|---|---|
| `integrity` | Is context structurally and epistemically trustworthy? | Validator findings, Readiness caps, ownership, provenance, contradictions, lifecycle state |
| `usefulness` | Did activated context support a real Mission with bounded relevant context? | package/handoff evidence, invalidation, additional retrieval, selected-versus-used evidence, discovered gaps |
| `learning` | What did execution teach that may justify governed context evolution? | Mission learning, outcomes, failures, Evolution Inbox items, decisions, update candidates |

Health dimensions must remain universal across organizational domains.
Execution evidence may be code and tests in Technology, campaign evidence in
Marketing, account evidence in Sales, financial records in Finance, contracts
in Legal, or other governed operational evidence.

---

## Status Model

Each signal and dimension uses an explainable status:

| Status | Meaning |
|---|---|
| `healthy` | Current evidence supports the expected condition |
| `attention` | Evidence identifies a non-blocking gap or degradation |
| `blocked` | Evidence identifies a condition that prevents safe use or transition |
| `unknown` | Available evidence cannot support a trustworthy conclusion |

`unknown` must never be silently treated as `healthy`.

The first report must not produce an aggregate numerical health score. A score
may be introduced only when evidence demonstrates stable meaning, calibration,
and decision value.

## Required Fields

| Field | Requirement |
|---|---|
| `schema` | Must equal `contextos.health.report/1` |
| `generated_at` | Observation timestamp |
| `root` | Assessed organizational/repository surface |
| `read_only` | Must be `true` |
| `summary` | Overall status and signal/candidate counts; no opaque score |
| `dimensions` | Integrity, usefulness, and learning dimensions with signals |
| `context_update_candidates` | Non-canonical suggested actions bound to source signals |
| `evidence_sources` | Embedded source schemas/summaries and observed Mission/Inbox evidence |
| `learning_boundary` | Explicit no-mutation and Construction-routing rules |
| `authority` | L1 suggestion authority and prohibited transitions |
| `constraints` | No Graph, Knowledge expansion, agents, connectors, or second lifecycle |
| `limitations` | Unknowns and evidence limits that prevent stronger claims |

---

## Signal Contract

Every signal must include:

- stable signal id,
- dimension and kind,
- status,
- belief state,
- human-readable message,
- evidence references,
- explicit `canonical: false`.

Signals are measurements or observations. Their presence in a report does not
make their interpretation canonical organizational truth.

---

## Context Update Candidate Contract

Every candidate must include:

- stable candidate id,
- kind and priority,
- title and rationale,
- suggested action,
- source signal references,
- lifecycle state `suggested`,
- `canonical: false`,
- required human review authority,
- route `existing_context_construction_lifecycle`,
- promotion prohibited in the Health capability.

The canonical route is:

```text
Health Evidence
-> Context Update Candidate
-> Human/Governed Review
-> Discovery / Construction Candidate
-> Draft
-> Review
-> Approval
-> Promotion
-> Canonical Validation
```

Context Health must reuse the v0.5 lifecycle. It must not create another truth
promotion mechanism.

## Evidence And Provenance

The first implementation may observe:

- Validator reports,
- Readiness reports,
- closed Mission artifacts,
- Activation Mission evidence,
- Evolution Inbox items,
- existing Construction authority and lifecycle contracts.

Literal evidence observed in Markdown remains narrative evidence. It may prove
that a Mission recorded a learning or invalidation event, but it may not prove
per-source consumption, causal effectiveness, or trend direction unless those
facts are represented explicitly.

### Mission-Use Evidence

The Mission-use object binds one exact Activation Package, Handoff, Mission,
and consumer to explicitly supplied execution evidence. It may represent:

- Governing Context selected at activation,
- selected sources with explicit access evidence,
- additional bounded Execution Context retrieval and its reason,
- missing, stale, invalid, or explicitly excluded context,
- context contributions to evidence or decisions,
- Mission outcome and evidence references.

Every assertion uses one evidence semantic:

| Semantic | Meaning |
|---|---|
| `observed` | Directly supported by runtime or Mission evidence |
| `declared` | Explicitly reported by the consumer but not independently observed |
| `derived` | Deterministically computed from observed evidence |
| `unknown` | Available evidence cannot support the claim |

The states remain distinct:

```text
Selected != Retrieved != Consumed != Used != Useful
```

Access does not prove consumption. Consumption does not prove use. Use does
not prove usefulness. Missing access evidence means `not_observed_accessed`,
not `unused`. Mission success does not prove that context caused the outcome.

Mission-use evidence is supplied explicitly. This contract does not authorize
ambient telemetry, surveillance monitoring, or opaque usefulness inference.

Trend claims require an explicit prior report or structured historical evidence.
A single current-state report must not invent a trend.

---

## Authority Boundary

The Health Engine operates at L1 Suggest authority.

It may:

- read governed evidence,
- classify current signals,
- expose unknowns,
- recommend context update candidates.

It may not:

- write drafts,
- approve candidates,
- promote context,
- mutate canonical context,
- resolve contradictions automatically,
- infer missing human decisions,
- create a second Construction lifecycle.

---

## Prohibited Behavior

This contract does not permit:

- autonomous canonical mutation,
- opaque or arbitrary health scoring,
- Context Graph runtime,
- Knowledge Engine expansion,
- agent orchestration,
- broad RAG,
- dashboards without operational value,
- external connectors,
- automatic remediation.

## Initial Implementation

```text
tools/health/health_engine/health_engine.py
tools/health/health_engine/report_builder.py
```

Public API:

```python
from health_engine.health_engine import ContextHealthEngine
from health_engine.mission_use_evidence import MissionContextUseEvidenceEngine

mission_use = MissionContextUseEvidenceEngine(".").run(
    package=package,
    handoff=handoff,
    selected_accesses=selected_accesses,
    execution_retrievals=execution_retrievals,
)
report = ContextHealthEngine(".").run(mission_use_evidence=mission_use)
```

Read-only CLI:

```text
contextos health --root . [--mission-use-evidence <report.json>]
                 [--format human|json] [--json-out <path>]
```

The CLI is an adapter over the public engine. It must not duplicate Health
classification, candidate generation, or epistemic logic.
