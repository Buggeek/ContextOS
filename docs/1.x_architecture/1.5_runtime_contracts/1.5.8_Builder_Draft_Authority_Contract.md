# 1.5.8 - Builder Draft Authority Contract

## Purpose

This contract defines the authority model required before Context OS may
create a draft context artifact.

It applies to future Builder behavior that turns
`contextos.builder.draft_plan/1` items into draft files or draft surfaces.

This contract does not authorize write-capable Builder behavior by itself. It
defines the minimum conditions a future implementation must satisfy.

---

## Central Rule

```text
Evidence may support a draft proposal.
Evidence must never silently become organizational truth.
```

Builder draft creation may move a context candidate only into `draft`.

It must never:

- auto-review,
- auto-approve,
- auto-promote,
- silently reinterpret evidence,
- overwrite existing canonical context,
- remove conflicting evidence,
- hide uncertainty,
- create organizational truth without authority.

---

## Lifecycle Boundary

Context Construction preserves this lifecycle:

```text
observed -> inferred -> suggested -> draft -> reviewed -> approved -> canonical/verified
```

Builder draft creation may perform only this transition:

```text
suggested -> draft
```

or, when updating an existing draft surface:

```text
draft -> draft
```

Builder draft creation must not perform:

- `observed -> reviewed`,
- `observed -> approved`,
- `observed -> canonical/verified`,
- `suggested -> reviewed`,
- `suggested -> approved`,
- `suggested -> canonical/verified`,
- `draft -> reviewed`,
- `draft -> approved`,
- `draft -> canonical/verified`.

Observed canonical artifacts may be reviewed or used as evidence, but they must
not be overwritten by draft creation.

---

## Required Inputs

A future draft write operation must consume preserved inputs. It must not
regenerate intent at write time.

Required inputs:

| Input | Required fields |
|---|---|
| Discovery Bundle | schema, source id, source fingerprint, artifact evidence, provenance |
| Construction Plan | schema, root, candidate ids, lifecycle state, evidence refs, discovery summary |
| Builder Draft Plan | schema, draft item ids, target paths, support, unknowns, contradictions, authority requirements |
| Mission Packet | mission id, owner, authority grants, constraints, success criteria |
| Human Draft Authorization | approving human identity, role, target draft item ids, target paths, plan identity, rationale |

The approved draft intent is the tuple:

```text
mission_id
builder_draft_plan_id_or_hash
draft_item_id
target_path
source_discovery_fingerprint
source_construction_candidate_id
authority_role
authorized_by
```

Any change to that tuple requires a new authorization.

---

## Evidence Sufficiency Rules

A draft item is eligible for future draft creation only when all are true:

1. The item status is `draftable`.
2. Support level is at least `moderate`.
3. The provenance chain contains a Discovery source id and fingerprint.
4. The provenance chain contains at least one evidence reference.
5. Unknowns are preserved in the future draft metadata.
6. Missing evidence is preserved in the future draft metadata.
7. Contradictions are empty.
8. The source Construction Plan has no blocking actions relevant to the item.
9. The Validator gate has no `error` or `fatal` findings for the target scope.

Evidence sufficiency does not mean truth sufficiency. It means only that a
draft proposal is permitted.

---

## Authority Requirements

Builder draft creation requires explicit L2 draft authority.

Minimum permission:

```yaml
permission:
  role: <authorized human-approved role>
  capability: builder.draft.create
  artifact_class: ssot-mom | ssot-roadmap | ssot-epic | operation | strategy | architecture | ...
  autonomy: L2
  scope:
    read:
      - <source evidence refs>
    write:
      - <draft target paths only>
    side_effects:
      - local_filesystem
  required_evidence:
    - contextos.discovery.bundle/1
    - contextos.construction.plan/1
    - contextos.builder.draft_plan/1
    - validator.gate
```

Human review is mandatory before draft creation. Human approval is mandatory
before any later promotion. The same human may authorize a draft only within
the role bounds declared by the Authority Model and Mission Packet.

Draft authority does not imply:

- approval authority,
- promotion authority,
- canonical write authority,
- deletion authority,
- overwrite authority.

---

## Target Path Scope

Draft writes must target draft surfaces only.

Allowed draft surfaces:

- an explicitly declared draft directory,
- a mission-scoped scratch/staging path,
- a branch or isolated worktree if the runtime supports it,
- another configured draft surface approved by mission authority.

Prohibited target paths:

- canonical SSOT paths unless the future operation is explicitly
  proposal-approved as a draft-only write surface,
- existing canonical artifacts,
- runtime configuration,
- decision records,
- generated evidence records from prior missions,
- any path outside the approved write scope.

For v0.5, create-only draft behavior is the safest future write model.

---

## No-Overwrite Guarantees

Builder draft creation must be no-overwrite by default.

Before write:

1. Resolve the target path.
2. Confirm it is inside the approved draft scope.
3. Confirm it does not already exist unless the operation explicitly targets a
   known draft surface with matching prior draft identity.
4. Refuse to replace canonical artifacts.
5. Refuse to delete, rename, or move existing content.
6. Refuse symlink traversal outside the approved root.

If a target exists unexpectedly, the operation must return an explicit
non-success state and perform no write.

---

## Drift Handling

The runtime must invalidate draft write eligibility when any relevant source
changes between authorization and write.

Relevant drift includes:

- Discovery source fingerprint changed,
- Builder Draft Plan identity/hash changed,
- Construction Plan candidate changed,
- target path state changed,
- Validator gate changed from passing to blocking,
- authority role or permission expired,
- evidence refs are missing,
- contradictions appeared,
- support level dropped below threshold.

The runtime must not silently regenerate a new Draft Plan and proceed.

---

## Validation Gates

Pre-write validation:

- input schemas are correct,
- Builder Draft Plan identity matches authorization,
- draft item is unchanged,
- target path is within approved draft scope,
- no-overwrite checks pass,
- repository/drift checks pass,
- Validator gate has no `error` or `fatal` findings for applicable scope,
- contradictions are empty,
- unknowns and missing evidence are preserved.

Post-write validation:

- only approved draft paths were created,
- created content is labeled as `draft`,
- provenance chain is embedded or attached,
- unknowns and missing evidence are embedded or attached,
- no canonical artifact was modified,
- Validator gate runs and outcome is recorded,
- result state is explicit.

Failed post-write validation must not be represented as success.

---

## Rollback / Reversibility

Rollback expectations:

- every created path records hash and provenance,
- rollback may remove only artifacts created by the same draft write operation,
- rollback must verify the current hash before removal,
- rollback must never remove pre-existing user content,
- rollback must never remove canonical context,
- rollback refusal must return explicit non-success evidence.

Draft writes should prefer reversible, create-only artifacts.

---

## Promotion Prohibition

Draft creation does not imply review, approval, or canonical verification.

Any later promotion must follow the Governance Protocol's Change-Proposal
Protocol:

```text
Propose -> Stage -> Validate -> Review -> Decide -> Apply -> Record -> Emit
```

The draft artifact may be evidence for that later proposal, but it is not
itself a decision.

---

## Universal Domain Model

This contract applies across organizational domains.

The runtime may vary artifact mappings by domain, but the authority model is
the same for:

- Strategy,
- Product,
- Marketing,
- Sales,
- Finance,
- Legal,
- People,
- Operations,
- Research,
- Data,
- Customer Success,
- Technology.

The universal rule is:

```text
domain evidence -> draft proposal -> human review -> human approval ->
canonical verification
```

---

## Minimum Future Runtime States

A future write-capable Builder should report at least:

| State | Meaning |
|---|---|
| `ineligible` | Required evidence, authority, or validation is missing |
| `eligible` | Pre-write checks pass, but no write has occurred |
| `confirmed` | Human has explicitly confirmed the exact draft write intent |
| `draft_created` | Approved draft paths were created |
| `failed_precheck` | No write occurred because a pre-check failed |
| `failed_write` | A write failed and result evidence is recorded |
| `failed_validation` | Post-write validation failed |
| `rolled_back` | Created artifacts were removed safely |
| `rollback_refused` | Rollback was unsafe or impossible |

---

## Out of Scope

This contract does not define:

- Knowledge Engine interpretation,
- semantic draft content generation,
- Context Graph runtime,
- agent orchestration,
- external connectors,
- automatic promotion,
- overwrite/repair workflows,
- decision-led canonical SSOT promotion implementation.
