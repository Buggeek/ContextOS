# 1.5.7 - Bootstrap Apply Approval Contract

## Purpose

This contract defines the governed transition from a read-only Guided Bootstrap
Plan to any future write-capable Bootstrap Apply operation.

It answers one question:

Under what conditions may Context OS modify a repository during Guided
Bootstrap?

The answer is:

Context OS may modify a repository only when a preserved Bootstrap Proposal has
been reviewed, approved by the required human authority, applied exactly as
approved, validated after mutation, and either accepted, failed, or rolled back
with evidence.

This contract does not authorize implementation of apply mode. It defines the
approval, evidence, validation, drift, no-overwrite, idempotency, and
reversibility rules a future implementation must satisfy.

---

## Scope

This contract applies to future Guided Bootstrap operations that would create
or modify repository-local Context OS artifacts such as:

- `.contextos/`
- `.contextos/manifest.yaml`
- `SSOT/`
- `SSOT/epics/`
- `docs/`
- `ops/`
- `templates/`
- minimum MOM or governance scaffolds

This contract does not apply to:

- external connector writes,
- Knowledge Engine writes,
- Context Graph runtime writes,
- agent activation,
- Mission Runtime implementation,
- generic workflow orchestration,
- product or strategy decisions.

---

## Relationship to Existing Artifacts

| Artifact | Role |
|---|---|
| `contextos.bootstrap.plan/1` | Read-only planning report; input to proposal creation |
| `contextos.bootstrap.proposal/1` | Preserved approval artifact for a specific apply candidate |
| `contextos.bootstrap.approval_record/1` | Read-only draft binding a preserved proposal to required human authority |
| `contextos.bootstrap.accepted_decision/1` | Accepted human decision artifact for the exact proposal identity; does not itself authorize apply |
| Mission Packet | Bounds the work and authority of the apply mission |
| Change Proposal | Governance mechanism for staged repository mutation |
| Decision Record | Required approval record for accepted L3+ repository mutation |
| Accountability Ledger | Append-only audit trail for L3+ action use |
| Validator Report | Pre-apply and post-apply gate evidence |
| Evolution Inbox | Captures deferred apply risks and ideas without changing active mission scope |

The Bootstrap Proposal reuses the existing Change-Proposal Protocol instead of
creating a parallel workflow.

---

## Bootstrap Proposal Schema

Future apply implementations must preserve a machine-readable proposal before
mutation.

```yaml
bootstrap_proposal:
  schema: contextos.bootstrap.proposal/1
  id: <stable proposal id>
  generated_at: <iso8601>
  expires_at: <iso8601 or null>
  root: <absolute target root at proposal time>
  mode: local | project | organization | embedded
  mission_id: <Mission Packet id>
  source_plan:
    schema: contextos.bootstrap.plan/1
    plan_ref: <path or report handle>
    plan_hash: <sha256 over canonical JSON plan>
    generated_at: <iso8601>
  repository_state:
    vcs: git | none | unknown
    base_ref: <branch, commit, or null>
    base_tree_hash: <hash over files relevant to proposed actions>
    dirty_state: clean | dirty | unknown
  authority:
    requested_by: <human or agent id>
    approving_roles: [<role>...]
    approvers: [<human id>...]
    authority_level: L3
    decision_ref: <Decision Record ref or null until approved>
    ledger_ref: <Accountability Ledger ref or null until applied>
    approval_state: planned | reviewed | approved | applied | validated | accepted | failed | rolled_back
  actions:
    - id: <bootstrap.action.*>
      type: create_directory | create_manifest | create_from_template | manual_remediation | validate_after_apply
      target_path: <relative path or null>
      class: automatic | approval_required | prohibited | manual
      source_template: <relative path or null>
      expected_before:
        exists: true | false | unknown
        hash: <sha256 or null>
      expected_after:
        exists: true | false
        hash: <sha256 or null>
      reversible: true | false
      rollback_strategy: delete_created | restore_previous | manual | none
      recommendation_ids: [<readiness recommendation id>...]
      evidence_refs: [<path or report ref>...]
  gates:
    pre_apply_validator_ref: <contextos.validator.report/1 ref>
    post_apply_validator_ref: <contextos.validator.report/1 ref or null>
  status: planned | reviewed | approved | applied | validated | accepted | failed | rolled_back
```

### Identity Rule

Apply must execute an approved proposal by `proposal.id` and `source_plan.hash`.
It must not silently regenerate a new plan and apply it.

If any proposed action, target path, source template, authority grant, or
repository state fingerprint changes, the proposal identity is invalidated and
a new review is required.

---

## Proposal Lifecycle

```text
planned -> reviewed -> approved -> applied -> validated -> accepted
                                             |            |
                                             |            -> failed -> rolled_back
                                             -> failed -> rolled_back
```

| State | Meaning | Required authority |
|---|---|---|
| planned | Proposal generated from a read-only Bootstrap Plan | Runtime may produce under read-only authority |
| reviewed | Human reviewer has inspected actions, evidence, risks, and blocked/manual items | Reviewer named by mode |
| approved | Required human authority accepts the exact proposal identity through `contextos.bootstrap.accepted_decision/1` | Mission Owner plus required mode authority |
| applied | Runtime performed only approved mutations | L3 execute-with-approval within proposal scope |
| validated | Post-apply Validator gates ran and produced evidence | Validator runs L4 read-only |
| accepted | Human authority accepts the validated result | Mission Owner plus required mode authority |
| failed | Apply or validation failed | Runtime or reviewer records failure |
| rolled_back | Reversible actions were reverted or manual rollback recorded | L3 within approved rollback scope |

Silent transition is forbidden. Every transition after `planned` must produce
evidence.

---

## Authority by Mode

| Mode | Use | Minimum authority data | Approval authority |
|---|---|---|---|
| local | Single local repository under one operator | operator id, target root, allowed paths, repository state fingerprint, Mission Packet id | Mission Owner acting as local Runtime Owner |
| project | Team/project repository | Mission Owner, Product Owner, Runtime Owner, maintainer or code-owner policy, allowed paths, proposal expiry, Decision Record target | Mission Owner plus Product Owner or Runtime Owner according to artifact class |
| organization | Multi-repository or organization-wide bootstrap | organizational governance roster, Runtime Owner, Product Owner, Maintainers, source scope, affected repositories, proposal expiry, Decision Record target, ledger target | Runtime Owner plus Governance Role; Product Owner for product/SSOT artifacts |
| embedded | Host product, IDE, CI, or agent surface invoking Context OS | host identity, user identity, tenant/project id, delegated scopes, callback approval handle, allowed paths, denied paths, proposal expiry | Host-confirmed human approver mapped to Mission Owner or Runtime Owner |

Minimum authority data for every mode:

- proposal id,
- mission id,
- requested-by identity,
- approving role(s),
- named approver(s),
- target root,
- allowed write paths,
- prohibited write paths,
- authority level,
- approval timestamp,
- expiration timestamp or explicit no-expiry rationale,
- Decision Record reference for L3+ apply,
- Accountability Ledger reference when ledger runtime exists.

If any of this data is missing, apply is prohibited.

---

## Action Classification

| Class | Meaning | Examples | Apply behavior |
|---|---|---|---|
| automatic | Safe only after proposal approval; deterministic and no-overwrite | create missing directory, create missing file from existing template | May run during approved apply |
| approval_required | Requires explicit human review even inside approved proposal | manifest creation, governance roster creation, SSOT scaffold creation | May run only when named in approved proposal |
| prohibited | Must not be performed by Guided Bootstrap apply | delete existing user files, overwrite non-generated content, modify external systems, infer verified truth | Must block proposal |
| manual | Requires human action outside apply | assign owner, resolve validator blocker, provide missing strategic input | Report only; apply must not perform |

Automatic does not mean unapproved. It means the action may execute without
additional per-action confirmation after the whole proposal is approved.

---

## Pre-Apply Evidence

Before mutation, an approved proposal must include:

1. Source Bootstrap Plan reference and canonical hash.
2. Readiness report summary used to generate the plan.
3. Validator report in `gate` mode for the target root.
4. Repository state fingerprint covering every target path and source template.
5. Action list with target paths, action classes, reversibility, and expected
   before/after state.
6. No-overwrite proof for every create action.
7. Blocked and manual action list.
8. Authority grant with mode, approvers, scope, expiry, and mission id.
9. Decision Record reference or staged decision placeholder.
10. Rollback plan for every reversible action and manual rollback statement for
    every non-reversible action.

Apply must not begin if the embedded Validator report contains `fatal`
findings. Apply must not begin if it contains `error` findings unless the
proposal classifies those findings as manual remediation and the affected
actions are blocked from mutation.

---

## Post-Apply Evidence

After mutation, the apply operation must produce:

1. Applied proposal id and source plan hash.
2. List of actions applied, skipped, blocked, failed, or rolled back.
3. File-level evidence for every mutation: path, previous existence, previous
   hash when available, new hash, and source template or generator id.
4. Post-apply Validator report in `gate` mode.
5. Git diff or equivalent repository delta when VCS exists.
6. Decision Record linking proposal, approvers, validator reports, and outcome.
7. Accountability Ledger event reference when ledger runtime exists.
8. Final state: `accepted`, `failed`, or `rolled_back`.

---

## Validator Gates

### Pre-Apply Gate

Run:

```text
contextos validate --root <target> --mode gate --format json
```

Requirements:

- Exit code 0 is eligible for apply.
- Exit code 7 is eligible only if every blocking finding is unrelated to the
  proposed mutation or converted into a manual/blocked action.
- Exit code 8 prohibits apply.
- Exit code 9 prohibits apply until configuration is corrected.

### Post-Apply Gate

Run the same gate after mutation.

Requirements:

- New `fatal` or `error` findings caused by apply require failure or rollback.
- Existing errors must not increase.
- Warnings may be accepted only when recorded in the Decision Record.
- The post-apply report must be preserved as evidence before acceptance.

---

## No-Overwrite Guarantees

Guided Bootstrap apply must never overwrite existing user content by default.

Rules:

1. Create actions may write only when the target path does not exist.
2. Directory creation is idempotent if the directory already exists.
3. Existing files become `skipped_existing` unless the proposal explicitly
   includes an approved replacement action. Replacement actions are prohibited
   in v0.4.
4. Generated files must include deterministic content or a recorded source
   template hash.
5. Symlink targets, path traversal, absolute target paths inside actions, and
   writes outside `root` are prohibited.
6. Hidden runtime files may be created only under `.contextos/`.

---

## Idempotency Expectations

Applying the same approved proposal twice must not create duplicate artifacts
or mutate already-created files.

Expected behavior:

- already-created directories are skipped,
- already-created files with the expected hash are skipped,
- already-created files with a different hash cause drift failure,
- manual actions remain manual,
- prohibited actions remain prohibited,
- repeated apply attempts append evidence rather than replacing prior evidence.

---

## Rollback and Reversibility

Every action must declare a rollback strategy.

| Strategy | Use |
|---|---|
| delete_created | A file or directory did not exist before apply and can be removed safely |
| restore_previous | Prior file content was captured and can be restored |
| manual | Human remediation is required |
| none | Action is non-reversible and therefore prohibited for v0.4 apply |

v0.4 apply may perform only reversible create actions and explicit manual
remediation reporting. Non-reversible mutation is prohibited.

Rollback is required when:

- apply writes outside approved scope,
- post-apply Validator introduces new `error` or `fatal` findings,
- proposal identity does not match approved state,
- repository drift invalidates expected before-state during apply,
- any approved action fails after earlier actions were already applied.

---

## Repository Drift Between Plan and Apply

Repository drift is any change to:

- target path existence,
- target path content hash,
- source template content hash,
- relevant validator inputs,
- Git base commit or tree hash,
- authority data,
- action list.

If drift is detected before apply, the proposal returns to `planned` and must
be regenerated or re-reviewed.

If drift is detected during apply, the operation fails before the affected
action and rolls back any already-applied reversible actions.

If drift is detected after apply, acceptance is blocked until a human reviewer
decides whether to accept, roll back, or create a follow-up mission.

---

## Approval State Storage

Approval state must use existing Context OS mechanisms:

1. Mission Packet: required for scope, constraints, acceptance criteria, and
   closure evidence.
2. Bootstrap Proposal artifact/report: required to preserve exact proposal
   identity and source plan hash.
3. Change Proposal: required when repository mutation is staged.
4. Accepted Decision artifact with embedded Decision Record: required before
   any future apply may consume an approved proposal.
5. Accountability Ledger entry: required when the ledger runtime exists; until
   then, mission evidence and commit history act as the temporary audit trail.

Mission evidence alone is sufficient for planning-only missions. It is not
sufficient for write-capable apply.

---

## Exit Conditions for Future Apply

A future write-capable apply mission may close as done only when:

- the approved proposal identity matches the applied proposal,
- all approved actions are applied, skipped, blocked, or rolled back with
  evidence,
- no prohibited actions were performed,
- no target path outside approved scope was touched,
- pre-apply and post-apply Validator reports are preserved,
- post-apply gate has no new blocking findings caused by apply,
- the Decision Record captures approval and outcome,
- rollback was executed or explicitly waived by human authority for any failed
  action.

---

## Versioning

The proposal schema is versioned as `contextos.bootstrap.proposal/<n>`.
Breaking changes require a Governance decision.
