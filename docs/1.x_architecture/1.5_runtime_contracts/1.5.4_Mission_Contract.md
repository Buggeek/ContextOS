# 1.5.4 — Mission Contract

## Purpose

A **Mission Packet** is the canonical unit of bounded, accountable execution
in Context OS. This contract specifies the Mission Packet's structure,
lifecycle states, ownership, and required evidence.

Mission Packets are produced and consumed by the **Mission Lifecycle**
defined in
[`3.4 Operational Lifecycle`](../../3.x_operation/3.4_COS_Operational_Lifecycle.md) §3.

Implementation is delegated to the Orchestrator role and the Runtime CLI
`contextos mission *` surface declared in
[`1.5.2 CLI Contract`](1.5.2_CLI_Contract.md).

Until Mission Runtime commands exist, self-hosted repository missions are stored
as SSOT execution artifacts using:

- `SSOT/E.4_Mission_[ID].md` for Mission Packets.
- `SSOT/E.5_Evolution_Inbox.md` for deferred ideas, risks, technical debt,
  opportunities, and hypotheses that must not alter active mission scope.

---

## Why a Mission Packet exists

Without an explicit packet:
- intent gets reinterpreted at each handoff,
- accountability becomes diffuse,
- evidence becomes informal,
- success criteria are debated post-hoc.

The Mission Packet binds intent, context, constraints, and success criteria
into a single artifact for the duration of the mission.

---

## Required Fields

```yaml
mission_packet:
  schema: contextos.mission.packet/1
  id: <ulid>
  title: <human-readable summary>
  intent: <multi-line statement of what is being asked and why>
  initiating_lifecycle: organization | product | release | feedback | governance | runtime | context-evolution
  owner: <human id>                # accountable person
  orchestrator: <agent id or "default">
  scope:
    in: [<artifact, system, area>...]
    out: [<exclusions>...]
  context_refs:                     # SSOT references the mission must consult
    - <path or graph selector>
  constraints:                      # hard constraints, including authority bounds
    - <statement>
  success_criteria:                 # observable; falsifiable
    - <statement>
  kill_criteria:                    # conditions under which mission is cancelled
    - <statement>
  evidence_plan:                    # how success or failure will be measured
    - <statement>
  authority_grants:                 # autonomy levels granted per role
    - role: <role>
      capability: <capability>
      level: L1 | L2 | L3 | L4 | L5
      bounds:
        read: [...]
        write: [...]
        side_effects: [...]
        resources: { tokens: <int>, time: <duration>, compute: <profile> }
  hypothesis_links:                 # when the mission tests a hypothesis
    - <hypothesis id>
  depends_on: [<mission id>...]     # optional ordering
  created_at: <iso8601>
  status: <see Lifecycle States>
```

Optional fields may be added; required fields are immutable except by the
mutation rules below.

### Context Version Binding

After the Context Version capability is available, a newly accepted Mission
should bind the exact governed context in force at Mission start:

```yaml
  context_version:
    id: context.version.<hash-prefix>
    identity_hash: <sha256>
    capture_event: mission_start
```

This is prospective. Historical Mission Packets without this binding remain
valid and must expose the continuity gap rather than fabricate a version.
Activation Package and Handoff references remain separate: they prove which
working context was delivered, while Context Version proves which governed
source state existed. The binding grants no additional Mission authority.

## Lifecycle States

```
draft ─► proposed ─► accepted ─► planned ─► executing ─► verifying ─►
       │                                                │
       │                                                ▼
       │                                            integrating
       │                                                │
       │                                                ▼
       └────────────► cancelled                      closed (done|cancelled|escalated)
```

| State | Meaning | Allowed transitions |
|---|---|---|
| `draft` | Being composed by a human or agent | → `proposed`, `cancelled` |
| `proposed` | Submitted for acceptance | → `accepted`, `cancelled` |
| `accepted` | Mission Owner has approved | → `planned`, `cancelled` |
| `planned` | Decomposed into tasks; team assembled | → `executing`, `cancelled` |
| `executing` | Specialized agents performing work | → `verifying`, `cancelled`, `escalated` |
| `verifying` | Verification Agent validating evidence | → `integrating`, `executing` (rework), `escalated` |
| `integrating` | Outputs being merged into SSOT | → `closed` |
| `cancelled` | Closed without delivery | terminal |
| `escalated` | Authority exceeded or unresolved conflict | → `planned` (after resolution) or `cancelled` |
| `closed` | Mission complete with outcome `done` or `cancelled` | terminal |

Transitions emit events
(see [`1.5.5 Runtime Event Model`](1.5.5_Runtime_Event_Model.md)).

---

## Ownership

| Role | Responsibility |
|---|---|
| **Mission Owner** | Human accountable for the mission outcome; signs off acceptance and closure |
| **Orchestrator** | Operational lead; decomposes, assembles, integrates |
| **Specialized Agents** | Execute within granted authority bounds |
| **Verification Agent** | Validates evidence against success criteria |
| **Context Guardian** | Integrates outputs into SSOT without semantic drift |

A mission with no Mission Owner is invalid.

---

## Evidence

Every closed mission must carry a verifiable **evidence trail**:

- Inputs consulted (artifact ids, graph selectors).
- Outputs produced (SSOT paths, decision records, diffs).
- Validation results (Context Health Report references).
- Authority ledger entries for every L3+ action.

Missions that cannot produce evidence are not eligible for `closed:done`.

---

## Mutation Rules

After `accepted`, the following are immutable:
- `intent`
- `success_criteria`
- `kill_criteria`
- `owner`
- `authority_grants` (broadening requires a new packet; narrowing is allowed
  with owner approval).

Mutable at any time before `closed`:
- `context_refs` (additions only; removals require justification)
- `evidence_plan` (refinements only)
- `depends_on` (additions and removals)

---

## Escalation

A mission must enter `escalated` when:
- Required context is missing or contradictory.
- An action would exceed granted autonomy.
- Success criterion cannot be met within `kill_criteria` window.
- Verification consistently fails for the same reason.

Escalation routes follow
[`3.6 Authority Model`](../../3.x_operation/3.6_COS_Human_Agent_Authority_Model.md)
§Escalation Rules.

---

## Anti-Patterns

- Missions without falsifiable success criteria.
- Missions without kill criteria.
- Missions that accumulate scope after `accepted`.
- Closing a mission without an evidence trail.
- Granting blanket authority instead of bounded `authority_grants`.
