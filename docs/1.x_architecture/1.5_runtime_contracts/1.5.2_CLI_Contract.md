# 1.5.2 — CLI Contract

## Purpose

The `contextos` CLI is the canonical human and automation entry point to the
Runtime. This contract specifies the command surface, argument shapes, output
shapes, exit codes, and authority bindings.

Implementation is delegated to **EPIC-008 Runtime CLI**.

---

## Design Principles

1. **Composable.** Each command has a single responsibility and returns
   structured output.
2. **Scriptable.** Every command supports `--format json` and writes results to
   stdout; logs go to stderr.
3. **Deterministic.** Same inputs + same repository state produce the same
   outputs.
4. **Authority-aware.** Commands declare which autonomy level they require to
   complete writes; reads default to L1.
5. **Idempotent where possible.** Read-only commands are deterministic for the
   same inputs and state; create-only writes refuse divergent replay.
6. **Observable.** Every implemented command returns structured report evidence.
   `cli.run` event emission remains a forward-looking integration with the
   [`1.5.5 Runtime Event Model`](1.5.5_Runtime_Event_Model.md), not v1.0 CLI
   behavior.

---

## Global Conventions

```text
contextos [--version] <command> [command options]
```

- Implemented commands accept command-local `--root`, which defaults to the
  current working directory.
- Implemented report commands accept `--format text|human|json`; JSON returns
  one pure report object on stdout.
- All commands write logs to stderr; data to stdout.
- All commands set exit codes per the table in §Exit Codes.

## Command Surface

### `contextos init`

Produce a Guided Bootstrap plan.

```text
contextos init [--root <path>] [--format text|human|json] [--json-out <path>]
contextos init [--root <path>] --proposal [--format text|human|json] [--json-out <path>]
contextos init [--root <path>] --approval-record <proposal.json> [--format text|human|json] [--json-out <path>]
contextos init [--root <path>] --accept-approval <approval.json> --accepted-by <human> --accepted-role <role> [--format text|human|json] [--json-out <path>]
contextos init [--root <path>] --preflight <accepted.json> [--format text|human|json] [--json-out <path>]
contextos init [--root <path>] --apply <preflight.json> --confirm-apply --confirmed-by <human> --confirmed-role <role> --confirmed-preflight-id <id> --confirmed-preflight-hash <hash> [--format text|human|json] [--json-out <path>]
```

**Effects and authority:** bare `contextos init`, proposal, approval-record,
acceptance, and preflight modes are read-only. `--apply` is create-only and
requires the complete explicit human confirmation and exact preflight binding
defined below. No mode may overwrite, replace, or delete existing content.

**Output:** Guided Bootstrap Plan report with schema
`contextos.bootstrap.plan/1`.

When `--proposal` is supplied, the command returns a read-only Bootstrap
Proposal report with schema `contextos.bootstrap.proposal/1`. A proposal freezes
the source plan hash, repository fingerprint, authority requirements, action
classifications, rollback metadata, and drift invalidation conditions. It does
not approve or authorize apply.

When `--approval-record <proposal.json>` is supplied, the command returns a
read-only Bootstrap Approval Record Draft with schema
`contextos.bootstrap.approval_record/1`. The draft binds a preserved proposal
to required authority, drift status, blockers, and a Decision Record draft. It
does not approve the proposal or authorize apply.

When `--accept-approval <approval.json>` is supplied, the command returns a
read-only Bootstrap Accepted Decision with schema
`contextos.bootstrap.accepted_decision/1`. Acceptance requires an explicit
human identity through `--accepted-by` and an explicit authority role through
`--accepted-role`. It verifies proposal identity, source plan identity,
repository fingerprint, proposal file hash, drift status, prohibited actions,
and required evidence before producing an embedded `contextos.decision/1`
Decision Record. It approves the preserved proposal as future apply intent, but
does not authorize or perform apply.

When `--preflight <accepted.json>` is supplied, the command returns a
read-only Bootstrap Apply Preflight report with schema
`contextos.bootstrap.apply_preflight/1`. Preflight verifies the accepted
decision, approval record, proposal, source plan binding, repository
fingerprint, authority, no-overwrite guarantees, rollback expectations, and
Validator gate, then freezes the exact executable mutation set. It may mark
apply eligible, but does not authorize or perform apply.

When `--apply <preflight.json>` is supplied, the command performs the first
write-capable Guided Bootstrap operation and returns
`contextos.bootstrap.apply_result/1`. Apply requires `--confirm-apply`,
`--confirmed-by`, `--confirmed-role`, `--confirmed-preflight-id`, and
`--confirmed-preflight-hash`. The confirmation must bind to the exact supplied
preflight. v0.4 apply is create-only: it may create only the approved mutation
actions in the preflight mutation set, refuses overwrite/replacement/deletion,
does not execute prohibited or manual actions, records mutation evidence, runs
post-apply Validator gate, and reports explicit success or failure.

**Output (json):**
```yaml
{
  "schema": "contextos.bootstrap.plan/1",
  "read_only": true,
  "summary": {
    "ready_for_bootstrap": true,
    "required_action_count": 0,
    "skipped_action_count": 0,
    "blocked_action_count": 0,
    "manual_action_count": 0
  },
  "actions": []
}
```

**Exit codes:** 0 plan/preflight/apply generated or executed successfully with
no blocking validator errors; 7 plan generated with embedded validator errors,
preflight generated but not eligible, or apply produced a failed result; 8
fatal validator findings; 9 misconfiguration.

Write-capable bootstrap behavior is exposed only through the explicit apply
surface that consumes a fresh eligible preflight and requires explicit human
confirmation. Bare `contextos init` remains safe to run as a planning command.
Real target apply requires target-specific human authority; testing authority
is limited to isolated fixtures unless otherwise granted. Apply satisfies
[`1.5.7 Bootstrap Apply Approval Contract`](1.5.7_Bootstrap_Apply_Approval_Contract.md)

### `contextos assess`

Run the Context Readiness Assessment for Release v0.3.

```text
contextos assess [--root <path>] [--format text|human|json] [--json-out <path>]
```

**Authority:** L4 read-only.

**Effects:** none. The command must not create, modify, or delete repository
files.

**Output:** Context Readiness Assessment report per
[`1.5.6 Context Readiness Assessment Contract`](1.5.6_Context_Readiness_Assessment_Contract.md).

**Exit codes:** 0 assessment generated without blocking Validator findings; 7
embedded Validator errors; 8 embedded Validator fatals; 9 misconfiguration;
64 usage error. Low readiness alone is reported in the assessment and is not a
CLI failure.

## Forward-Looking Reserved Surface

The following commands are architecture reservations and are not implemented
in the v1.0 CLI. Their presence in this contract grants no runtime capability
or authority.

### `contextos sources <subcommand>` (forward-looking)

Manage the Connector Manifest (Bootstrap Step 1).

```text
contextos sources add <type> <reference> [--scope read|read-write] [--owner <id>]
contextos sources list
contextos sources remove <id>
```

**Authority:** L2 (writes manifest).

**Output (json) for `list`:**
```yaml
{
  "sources": [
    { "id": "<ulid>", "type": "<type>", "reference": "<ref>", "scope": "<scope>", "owner": "<id>" }
  ]
}
```

**Exit codes:** 0 success; 2 source registration failure (connectivity, auth, schema).

---

### `contextos governance set-roster` (forward-looking)

Declare initial governance roster.

```text
contextos governance set-roster
  --maintainer <id> [--maintainer <id>...]
  --product-owner <id>
  --runtime-owner <id>
```

**Authority:** L3 (gated on `--confirm` or interactive prompt).

**Idempotent:** yes (last write wins; previous roster archived in ledger).

**Exit codes:** 0 success; 3 invalid roster.

### `contextos scan` (forward-looking)

Run Discovery (Bootstrap Step 3).

```text
contextos scan [--source <id>...] [--out <path>]
```

**Authority:** L2 (reads external systems; writes discovery output bundle).

**Output:** Discovery output bundle path on stdout.

**Exit codes:** 0 success; 4 scan failure (any registered source unreachable
unless `--skip-unreachable`).

### `contextos build-mom` (forward-looking)

Build or update MOM drafts (Bootstrap Step 6).

```text
contextos build-mom [--from <discovery-bundle>] [--from-knowledge <bundle>]
                    [--out SSOT/]
```

**Authority:** L3 (writes SSOT drafts; requires governance roster present).

**Output:** list of MOM artifact paths produced, each with Hypothesis vs
Verified tagging metadata.

**Exit codes:** 0 success; 5 build failure (missing inputs, taxonomy violation).

---

### `contextos build-ssot` (forward-looking)

Promote MOM drafts to SSOT (Bootstrap Step 7).

```text
contextos build-ssot [--accept-hypotheses <list>] [--reject <list>]
```

**Authority:** L3 (requires Product Owner approval for product artifacts).

**Output:** SSOT diff summary.

**Exit codes:** 0 success; 6 promotion failure (governance gate, validation).

### `contextos validate`

Run the Validator (Bootstrap Step 8 + routine use).

```text
contextos validate [--mode install-check|pre-bootstrap|full|gate]
                   [--rules <selector>]
                   [--format text|human|json] [--json-out <path>]
```

**Authority:** L4 read-only.

**Output:** Validator Report (machine + human) per
[`1.5.1 Validator Contract`](1.5.1_Validator_Contract.md).

**Exit codes:** 0 / 7 / 8 / 9 per Validator Contract.

### `contextos health`

Produce the read-only Context Health & Learning report.

```text
contextos health [--root <path>]
                 [--mission-use-evidence <context-use.json>]
                 [--format text|human|json]
                 [--json-out <path>]
```

**Authority:** L4 read-only.

**Effects:** none. The command must not create, modify, remediate, or promote
organizational context.

**Output:** `contextos.health.report/1` per
[`1.5.10 Context Health Report Contract`](1.5.10_Context_Health_Report_Contract.md).
The human representation must expose Integrity, Usefulness, Learning,
evidence semantics, attention/blocking/unknown signals, observability limits,
and governed Context Update Candidates. JSON stdout must contain only the
machine report.

When `--mission-use-evidence` is supplied, the input must use
`contextos.mission.context_use_evidence/1` and match the assessed root. The CLI
passes it to the Health Engine without reinterpreting context use. Access or
Mission success must not become an inferred usefulness claim.

**Exit codes:** 0 report generated without blocking Validator findings; 7
embedded Validator errors; 8 embedded Validator fatals; 9 misconfiguration.

### `contextos activate`

Create, check, or render a Handoff from a read-only Context Activation Package.

```text
contextos activate --goal <text> [--mission-id <id>] [--consumer <type>]
                   [--max-artifacts <n>]
                   [--format text|human|json] [--json-out <path>]
contextos activate --check-package <package.json> [--handoff]
                   [--format text|human|json] [--json-out <path>]
contextos activate --check-handoff <handoff.json>
                   [--format text|human|json] [--json-out <path>]
```

**Authority:** L1 read-only. Consumer identity and permissions are bound inputs;
the command grants no mutation, promotion, or delegated authority.

**Output:** `contextos.activation.package/1`,
`contextos.activation.package_check/1`, `contextos.activation.handoff/1`, or
`contextos.activation.handoff_check/1` per the
[Context Activation Package Contract](1.5.9_Context_Activation_Package_Contract.md).

**Exit codes:** 0 valid read-only output; 7 invalidated Package/Handoff or
blocking Validator findings; 8 fatal Validator findings; 9 misconfiguration.

### `contextos memory`

Retrieve or check bounded Organizational Memory prior art without replacing
current Context Activation.

```text
contextos memory --goal <text> [--mission-id <id>] [--question <text>]
                 [--consumer <type>] [--purpose <text>]
                 [--organizational-mode <mode>] [--actor-role <role>]...
                 [--authority-scope <scope>]
                 [--retention-policy <json>]...
                 [--memory-metadata <json>] [--evaluation-time <iso8601>]
                 [--limit <1-50>]
                 [--format text|human|json] [--json-out <path>]
contextos memory --check-retrieval <retrieval.json>
                 [--retention-policy <json>]...
                 [--memory-metadata <json>] [--evaluation-time <iso8601>]
                 [--format text|human|json] [--json-out <path>]
```

**Authority:** L4 read-only. Actor roles and authority scope are policy inputs;
the command does not grant authority. Relevant memory remains unexposed unless
exact Retention Resolution returns `normal` with sufficient metadata
visibility. No applicable policy remains `unknown`.

**Effects:** none. Retrieval binds the exact
`contextos.memory.continuity_report/1` and current
`contextos.activation.package/1` states. It does not add memory to Governing
Context, infer applicability or usefulness, or mutate canonical Context.

**Output:** `contextos.memory.retrieval_result/1` or
`contextos.memory.retrieval_check/1` per
[`1.5.12 Organizational Memory Retrieval Contract`](1.5.12_Organizational_Memory_Retrieval_Contract.md).

**Exit codes:** 0 retrieval/check valid; 7 blocking Validator findings or
invalidated retrieval; 8 fatal Validator finding; 9 misconfiguration.

### `contextos reason`

Create or check a governed read-only Contextual Assessment.

```text
contextos reason --goal <text> [--mission-id <id>] [--question <text>]
  [--consumer <id>] [--purpose <text>]
  [--organizational-mode local|project|organization|embedded]
  [--actor-role <role>...] [--authority-scope <scope>]
  [--retention-policy <policy.json>...]
  [--memory-metadata <metadata.json>]
  [--context-version <version.json>...]
  [--mission-use-evidence <evidence.json>]
  [--reasoning-evidence <evidence-set.json>]
  [--focus-entity <entity>...]
  [--evaluation-time <timestamp>] [--memory-limit <n>]
  [--format text|human|json] [--json-out <path>]

contextos reason --check-assessment <assessment.json>
  [--retention-policy <policy.json>...]
  [--memory-metadata <metadata.json>]
  [--format text|human|json] [--json-out <path>]
```

**Authority:** L1 inspect/suggest. The command may observe, derive bounded
interpretations, form hypotheses, and recommend. It may not decide, approve,
execute, change policy, or mutate canonical context.

**Effects:** none. Structured evidence and historical context are exact inputs;
the CLI performs no reasoning or policy interpretation itself.

**Output:** `contextos.reasoning.assessment/1` or, for saved-result validation,
`contextos.reasoning.assessment_check/1` per the
[Contextual Assessment Contract](1.5.15_Contextual_Assessment_Contract.md).

JSON stdout must contain the report only. `--json-out` writes the complete
machine report. A saved Assessment check must re-run its exact bound Goal,
Mission, consumer, temporal basis, Context Versions, Mission-use evidence,
structured evidence, and current Runtime state. Any changed or missing policy,
metadata, source, permission, authority, or evidence input invalidates reuse.

**Exit codes:** 0 Assessment generated with no blocking Validator findings or
saved Assessment remains exact; 7 blocking Validator findings or invalidated
saved Assessment; 8 fatal Validator findings; 9 misconfiguration.

## Exit Codes (canonical)

| Code | Meaning |
|---|---|
| 0 | Success |
| 1 | Reserved |
| 2-6 | Reserved for forward-looking command surfaces |
| 7 | Blocking findings, ineligible governed transition, failed write validation, or invalidated saved result |
| 8 | Fatal Validator finding embedded in an implemented command result |
| 9 | Misconfiguration |
| 64 | Usage error (bad args) |

## JSON Output Shape Discipline

Every `--format json` invocation returns a single top-level JSON object.
Commands with a canonical report contract may return that report object
directly, identified by its `schema` field. Other commands return either
`result` or `error`. Errors include `code`, `message`, `category`, and
optional `evidence`.

```yaml
{ "schema": "contextos.readiness.report/1", ... }
# or
{ "result": { ... } }
# or
{ "error": { "code": 2, "category": "sources", "message": "...", "evidence": {...} } }
```

## Authority Summary

| Command | Required autonomy | Notes |
|---|---|---|
| `init` | L4 read-only except explicit apply | Plan through preflight are read-only; create-only apply requires exact human confirmation and governed authority |
| `assess` | L4 read-only | Readiness assessment; no writes |
| `validate` / `health` | L4 read-only | Read-only audit |
| `reason` | L1 inspect/suggest | Read-only advisory reasoning; no Decision or execution authority |
| `memory` | L4 read-only | Bounded prior-art retrieval/check; no authority transfer |
| `activate` | L1 read-only | Derived working context; no authority transfer |

Forward-looking `sources`, `governance`, `scan`, `build-mom`, `build-ssot`, and
`mission` authority requirements remain design constraints only until those
surfaces are implemented and verified.
