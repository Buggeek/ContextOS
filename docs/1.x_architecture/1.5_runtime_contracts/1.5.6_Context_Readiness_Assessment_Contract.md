# 1.5.6 — Context Readiness Assessment Contract

## Purpose

The Context Readiness Assessment is the central product capability of
Release v0.3. It is a read-only Runtime assessment that answers four
first-time user questions:

- What context exists here?
- What context is missing?
- How ready is this repository or organization for Context OS?
- What should I do next?

The assessment converts a local repository from an opaque collection of files
into an understandable Context OS readiness state. It does not initialize,
bootstrap, scan external systems, build artifacts, mutate documents, activate
agents, or infer unverified organizational truth.

Implementation is delegated to v0.3 slices of EPIC-004, EPIC-006, EPIC-007,
and EPIC-008.

---

## Definition

Context Readiness is the degree to which a repository or organization has the
minimum visible context, structure, governance signals, and runtime rails
needed to proceed safely into the Context OS journey:

```text
Assess -> Bootstrap -> Construct -> Activate -> Learn -> Reason
```

Readiness is not the same as Runtime Maturity. Readiness is a local
precondition assessment; maturity describes the operational capability of a
Runtime instance over time.

---

## Scope

The v0.3 assessment may use:

- Local repository inventory.
- Existing Context OS artifacts under `docs/`, `SSOT/`, `ops/`, and
  `templates/`.
- Existing runtime files such as `.contextos/manifest.yaml` when present.
- ValidatorEngine output from EPIC-007.
- Static README, roadmap, governance, epic, and contract artifacts.

The v0.3 assessment must not use:

- Knowledge Engine interpretation.
- Context Builder writes.
- Context Graph runtime.
- Agent runtime.
- External connectors.
- Automatic document mutation.
- Silent bootstrap or scaffold creation.

---

## Evaluation Dimensions

The assessment evaluates six dimensions. Each dimension is scored from 0 to
100 and then weighted into the overall score.

| ID | Dimension | Weight | What it measures |
|---|---:|---:|---|
| `inventory` | Context Inventory | 20 | Whether Context OS-relevant files, folders, and source signals are visible |
| `structure` | Structural Integrity | 20 | Whether files, naming, taxonomy, links, and paths are coherent |
| `governance` | Governance & Ownership | 20 | Whether ownership, authority, DoR/DoD, and governance signals are present |
| `operational_map` | Operational Map Completeness | 15 | Whether MOM/SSOT artifacts provide a usable map of the work |
| `runtime` | Runtime Enablement | 15 | Whether Validator, CLI, manifest, and local runtime rails are available |
| `source_evidence` | Source Evidence | 10 | Whether local sources provide enough evidence for bootstrap and construction |

### Dimension Signals

| Dimension | Positive signals | Gap signals |
|---|---|---|
| `inventory` | README, docs taxonomy, SSOT, epics, operations docs, templates, examples | Missing canonical folders, empty SSOT, no operational artifacts |
| `structure` | Validator has zero blocking findings; links and taxonomy are coherent | Validator `error`/`fatal`, broken links, legacy paths, naming drift |
| `governance` | Owners, Governance Protocol, DoR/DoD, authority model, accountability artifacts | Missing owners, missing roster, unclear authority, no decision trail |
| `operational_map` | Vision, roadmap, MOM-like artifacts, product/system/governance maps | No product map, no system map, no success/kill criteria, weak SSOT |
| `runtime` | ValidatorEngine available, `contextos validate` works, manifest present or clearly absent, tests present | Missing manifest, no CLI surface, validator misconfiguration |
| `source_evidence` | Local code/docs/examples can be inventoried and cited | No source evidence, no examples, no local signals for construction |

---

## Scoring Model

Each dimension produces:

```yaml
dimension:
  id: inventory | structure | governance | operational_map | runtime | source_evidence
  score: 0..100
  weight: 0..100
  status: excellent | good | partial | weak | blocked
  signals: [<positive observations>]
  gaps: [<missing or weak observations>]
  evidence_refs: [<relative paths>]
```

The overall score is the weighted sum of dimension scores:

```text
overall_score =
  inventory * 0.20 +
  structure * 0.20 +
  governance * 0.20 +
  operational_map * 0.15 +
  runtime * 0.15 +
  source_evidence * 0.10
```

The score is rounded to the nearest integer.

### Score Caps

Score caps prevent false confidence:

| Condition | Maximum level |
|---|---|
| Repository cannot be read | R0 |
| Assessment cannot produce a machine report | R0 |
| Validator returns `fatal` | R0 |
| Validator returns `error` findings | R2 |
| No Context OS-relevant artifacts are found | R1 |
| Governance ownership is absent | R3 |
| Runtime manifest is absent | R4 |

Warnings do not make the assessment fail. They reduce dimension scores and
generate recommendations.

---

## Readiness Levels

| Level | Score | Name | Meaning | Next step |
|---|---:|---|---|---|
| R0 | 0-19 | Unassessable | The repository cannot be evaluated reliably | Fix access or fatal input issues |
| R1 | 20-39 | Unstructured | Context is mostly implicit or scattered | Add minimum visible context |
| R2 | 40-59 | Inventory Ready | Enough local context exists to map gaps | Remediate blockers and prepare bootstrap |
| R3 | 60-74 | Bootstrap Ready | The repo has enough signal for guided bootstrap | Run guided bootstrap in v0.4 |
| R4 | 75-89 | Construction Ready | Structured context and governance are strong enough for draft construction | Enter Context Construction in v0.5 |
| R5 | 90-100 | Operational Context Ready | Context is coherent, governed, and ready for later activation/learning slices | Maintain readiness and prepare activation |

The v0.3 product goal is not to force every repository to R5. The goal is to
produce an honest assessment and actionable next steps.

---

## Human Report

The human-readable report must show, in this order:

1. Repository/root assessed.
2. Overall score and readiness level.
3. One-sentence answer to "what should I do next?"
4. Dimension score table.
5. Context inventory summary.
6. Validator summary.
7. Top recommendations, grouped by priority.
8. Missing or deferred capabilities.
9. Evidence references.

The report must avoid implementation tutorial text. It should present the
state of the repository and the next action clearly enough that a first-time
user can decide whether to remediate, bootstrap, or continue constructing
context.

---

## Machine Report

The machine-readable report schema is:

```yaml
report:
  schema: contextos.readiness.report/1
  generated_at: <iso8601>
  root: <absolute path>
  mode: repository
  summary:
    score: 0..100
    level: R0 | R1 | R2 | R3 | R4 | R5
    level_name: <string>
    can_bootstrap: <bool>
    can_construct: <bool>
    blocking_issue_count: <int>
    recommendation_count: <int>
  dimensions:
    inventory:
      score: 0..100
      weight: 20
      status: excellent | good | partial | weak | blocked
      signals: [<string>]
      gaps: [<string>]
      evidence_refs: [<relative path>]
    structure: { ... }
    governance: { ... }
    operational_map: { ... }
    runtime: { ... }
    source_evidence: { ... }
  inventory:
    artifact_counts:
      docs: <int>
      ssot: <int>
      epics: <int>
      ops: <int>
      templates: <int>
      examples: <int>
    present_artifacts: [<relative path>]
    missing_artifacts: [<artifact id or path>]
  validator:
    schema: contextos.validator.report/1
    summary:
      rules_run: <int>
      info: <int>
      warn: <int>
      error: <int>
      fatal: <int>
      exit_code: <int>
    top_findings:
      - id: <validator finding id>
        rule: <category.rule>
        severity: info | warn | error | fatal
        path: <relative path or null>
        message: <string>
  recommendations:
    - id: readiness.<category>.<action>
      priority: P0 | P1 | P2 | P3
      category: coverage | structure | governance | ownership | runtime | source_evidence | construction | deferred
      title: <string>
      rationale: <string>
      target_journey_step: assess | bootstrap | construct | activate | learn | reason
      related_epic: EPIC-004 | EPIC-006 | EPIC-007 | EPIC-008 | null
      evidence_refs: [<relative path>]
      suggested_next_action: <string>
      authority_required: L0 | L1 | L2 | L3 | L4 | L5
  constraints:
    read_only: true
    external_connectors_used: false
    knowledge_engine_used: false
    graph_runtime_used: false
    documents_mutated: false
```

Implementations may include additional fields, but they must preserve all
required fields above and must not change field meaning without a schema
version bump.

---

## Recommendation Taxonomy

Recommendation ids are stable and use:

```text
readiness.<category>.<action>
```

Categories:

| Category | Purpose | Example IDs |
|---|---|---|
| `coverage` | Missing context artifacts or weak artifact coverage | `readiness.coverage.add_product_map` |
| `structure` | Taxonomy, naming, path, link, or markdown issues | `readiness.structure.fix_broken_links` |
| `governance` | Missing governance rules, DoR/DoD, authority, policy | `readiness.governance.declare_roster` |
| `ownership` | Missing owner/accountability data | `readiness.ownership.assign_artifact_owner` |
| `runtime` | Missing or weak local runtime rails | `readiness.runtime.create_manifest` |
| `source_evidence` | Missing local source evidence for future Discovery | `readiness.source_evidence.add_examples` |
| `construction` | Preparation for MOM/SSOT draft construction | `readiness.construction.prepare_mapping` |
| `deferred` | Explicitly deferred future capability | `readiness.deferred.skip_knowledge_engine` |

Priorities:

| Priority | Meaning |
|---|---|
| P0 | Blocking: assessment cannot be trusted or a future gate cannot run |
| P1 | Required before guided bootstrap or construction |
| P2 | Should improve readiness but does not block the next step |
| P3 | Informational or future-facing |

Deferred recommendations must explain why a capability is intentionally not
part of v0.3.

---

## CLI Binding

The v0.3 CLI surface for this contract is:

```text
contextos assess [--root <path>] [--format text|human|json] [--json-out <path>]
```

Behavior:

- Runs read-only local repository inventory.
- Invokes ValidatorEngine for structural and governance signals.
- Produces a Context Readiness Assessment report.
- Writes JSON only to stdout when `--format json` is used.
- May write the same machine report to `--json-out`.
- Does not treat low readiness as a CLI failure.

Exit codes:

| Code | Meaning |
|---|---|
| 0 | Assessment report generated |
| 8 | Assessment could not complete due to fatal input/runtime failure |
| 9 | Assessment misconfiguration |
| 64 | Usage error |

---

## v0.3 Acceptance Criteria

Release v0.3 is complete when:

- The Context Readiness Assessment contract is current and referenced by the
  roadmap, SSOT roadmap, and active v0.3 epic slices.
- `contextos assess` produces human and JSON reports conforming to
  `contextos.readiness.report/1`.
- The assessment uses only local repository inventory and ValidatorEngine
  output.
- The assessment is read-only and leaves the working tree unchanged.
- The current Context OS repository can dogfood the assessment.
- At least one example repository can be assessed.
- Reports answer the four first-time user questions directly.
- Recommendations use the taxonomy in this contract.
- `contextos validate --mode gate` still passes for this repository.
- Validator and CLI tests remain green.

---

## Authority

The assessment runs at autonomy **L4 read-only**. It may inspect, summarize,
score, and recommend. It must not apply fixes, create artifacts, modify
configuration, or activate agents.

---

## Versioning

The readiness report schema is versioned as
`contextos.readiness.report/<n>`. Breaking changes require a Governance
decision and a schema version bump.
