# 1.5.14 - Context Version Contract

## Purpose

Define the immutable identity and provenance record for the governed context
state in force at a meaningful organizational event.

Machine schemas:

```text
contextos.context.version_capture_plan/1
contextos.context.version_capture_plan_check/1
contextos.context.version/1
contextos.context.version_check/1
```

A Context Version is not a copy of context. It identifies exact governed
sources, versions, fingerprints, authority, policy, event, and temporal
evidence so historical work can be interpreted without rebuilding old truth
from current files.

---

## Product Question

> What exact governed organizational context was in force when this Mission,
> Decision, Approval, Promotion, Release, policy change, or explicit checkpoint
> occurred?

The answer is evidence, not authority. Remembering a historical state does not
make it current or canonical now.

---

## Canonical Boundaries

```text
Current Context != Historical Context
Historical Context != Invalid Context
Context Version != Context Copy
Context Version != Activation Package
Context Version != Git Commit
Context Version != Memory Retrieval
Superseded != Deleted
Remembered != Canonical Authority
```

- Canonical source systems remain authoritative for their content.
- A Context Version embeds no source content, excerpts, or reconstructed truth.
- An Activation Package records selected Working Context for a consumer and
  Mission. A Context Version records the governed source state at an event.
- Git may prove a filesystem implementation snapshot. It is optional
  implementation evidence and never the universal Context Version identity.
- Version history grants no permission, approval, promotion, or current
  applicability.

---

## Lifecycle

```text
Current governed source state
-> Context Version Capture Plan
-> Plan check
-> Immutable Context Version
-> Historical version check
-> Organizational Memory lineage
```

The capture plan is a read-only pre-capture calculation. It may become stale
before capture. Capture consumes the exact valid plan and does not silently
regenerate it.

The captured version is immutable. Later source changes do not invalidate its
historical identity. A later version records its parent/superseded version;
the prior object is never rewritten to point forward.

---

## Meaningful Capture Events

The minimum accepted event vocabulary is:

```text
mission_start
consequential_decision
accepted_approval
canonical_promotion
release_cut
material_policy_change
material_governance_change
explicit_human_checkpoint
```

These events have current product evidence because they already freeze
governing context, exercise authority, change canonical state, or create
consequential organizational evidence.

Routine file changes, command executions, report generation, source reads,
and background intervals are not capture events. Mission completion normally
references the Mission-start version unless a consequential event above
created another version.

Automatic hooks, background capture, and capture of every source modification
are deferred. Capture is explicit to avoid version explosion.

---

## Capture Plan

`contextos.context.version_capture_plan/1` binds:

- organization, domain, tier, and context-root scope;
- exact capture event, rationale, Mission, Goal, and triggering evidence;
- exact capture temporal basis;
- canonical source identities, locators, versions, lifecycle states, and
  fingerprints;
- authority-model and policy references;
- source-of-record adapters;
- Activation Package and Handoff references when actually used;
- optional parent Context Version identity/hash;
- optional implementation snapshot evidence;
- Validator gate evidence;
- continuity gaps, unknowns, and limitations.

The plan is ready only when:

- every source is present and fingerprinted;
- the Activation Package/Handoff bindings supplied for the event are valid;
- the Validator gate has no errors or fatals;
- the event type is accepted;
- scope, Mission/event identity, and temporal basis are explicit.

Plan identity excludes report-generation time and root location. It includes
the exact source manifest and all governed bindings.

`contextos.context.version_capture_plan_check/1` recomputes the plan from the
same explicit inputs. Source, package, Handoff, scope, event, authority,
policy, parent, or temporal drift invalidates the plan.

## Context Version Required Fields

```yaml
context_version:
  schema: contextos.context.version/1
  id: context.version.<hash-prefix>
  identity_hash: <sha256>
  immutable: true
  content_embedded: false
  scope:
    organization: <id>
    domain: <universal organizational domain>
    tier: working | project | organizational
    context_root: <logical context root>
  temporal:
    captured_at: <iso8601>
    effective_from: <iso8601>
    effective_until: <iso8601 or null>
  capture:
    event_type: <accepted event>
    reason: <rationale>
    mission_id: <id or null>
    goal: <text or null>
    triggering_event: <typed reference or null>
  source_manifest:
    - source_id: <stable identity>
      source_of_record: {adapter: <type>, locator: <opaque locator>}
      fingerprint: {algorithm: sha256, value: <hash>}
      authority_tier: <declared tier>
      lifecycle_state: <state at capture>
      truth: {epistemic_support: null, governance_lifecycle: null, strategic_belief: null}
      content_embedded: false
  source_fingerprint: <stable manifest hash>
  bindings:
    activation_package: <id/hash or null>
    activation_handoff: <id/hash or null>
    authority_refs: []
    policy_refs: []
  lineage:
    parent_version: <id/hash or null>
    supersedes: <id or null>
    superseding_version: null
  implementation_evidence: <optional adapter-specific evidence>
  truth_summary: <three-axis counts and unclassified counts>
  retention: <independent retention metadata>
  provenance: <capture engine and exact plan identity>
  continuity_gaps: []
  authority: {granted_by_version: false}
```

Source identity and fingerprint are separate. Identity says which governed
source; fingerprint says which exact state. Current filesystem locators are
paths. Future systems may use policy, record, dataset, contract, campaign,
account, financial, operational, or other stable source identities without
changing this model.

---

## Identity And Immutability

The version identity binds every field above except report-generation metadata
and absolute runtime root.

- Capturing the same valid plan is idempotent.
- Changing any bound value creates a different version.
- Captured versions are never edited or regenerated under an existing id.
- A later version may cite a prior version as parent and superseded state.
- Forward supersession is represented by later lineage evidence, not by
  mutating the prior version.

Persistence is outside this first primitive. A consumer may preserve the exact
machine object, but the Runtime does not create a version registry, alter SSOT,
or hook other commands automatically.

---

## Historical Verification

`contextos.context.version_check/1` reports independent historical,
content-freshness, profile, target-canonical, and implementation states:

1. **Immutable identity:** valid or tampered.
2. **Historical source verification:** verified, partial, or unverifiable.
3. **Selected-source content currentness:** current, material drift, or unknown.
4. **Adoption Profile currentness:** current, material drift, or not applicable.
5. **Target canonical currentness:** current, material drift, or unknown.
6. **Repository-tip state:** exact capture tip, advanced,
   different-or-divergent, or unknown.
7. **Current applicability:** exact current match, superseded-or-drifted, or
   unknown, retained for compatibility.

The implementation reference captured by a filesystem/Git adapter and the
current repository tip are evidence about implementation history. They are not
the Context Version identity and do not determine content currentness by
themselves.

If the repository tip advances while every selected governed source and the
exact Adoption Profile remain current, the check reports
`irrelevant_repository_advancement: true` and preserves exact current
applicability. If any selected source or profile binding changes, the check
reports material drift even when the repository tip is unchanged.

```text
Repository Tip Changed != Selected Context Stale
Selected Source Or Profile Drift = Material Context Drift
```

For the filesystem adapter, the check first compares current source hashes. If
a source changed and an exact Git implementation reference was captured, the
check may verify the historical blob at that commit. This proves source
availability, not universal authority or current applicability.

An unavailable source keeps its recorded identity and fingerprint. The check
reports the gap and never fabricates content from current files.

---

## Activation Relationship

```text
Context Version
-> Activation Package
-> Handoff
-> Mission
-> Decision / Outcome / Learning
```

The relationship is complementary:

- Context Version: what governed source state existed at the event.
- Activation Package: which relevant current sources were selected.
- Handoff: what compact package-backed orientation was delivered.
- Mission-use evidence: what was accessed or used during execution.

Package and Handoff identities may be bound to a version only when exact
artifacts existed and validated. Their content is not copied into the version.

---

## Memory And Retention

Missions, Decisions, Evidence, Outcomes, Learning, and context-state
transitions may cite an exact Context Version id/hash. Retrieval may later use
that binding as historical evidence, but the version confers no relevance,
applicability, authority, or usefulness by itself.

Context Versions are `context_state` memory for retention-policy purposes.
Version metadata and referenced content remain independently governable. A
version may remain while content becomes restricted, archived, unavailable, or
subject to hold. This contract executes no retention transition.

---

## Truth Axes

Context Version is temporal/provenance evidence, not a fourth truth axis.
Each source preserves its state at capture where exact evidence exists:

- epistemic support: observed, declared, inferred, derived, unknown;
- governance lifecycle: suggested, draft, reviewed, approved, canonical;
- strategic belief: hypothesis, verified, deprecated.

Missing axis evidence stays unclassified. The Runtime must not normalize a
historical source using its current lifecycle state.

---

## Authority And Side Effects

Planning, capture, and checks are read-only. They may not:

- copy or mutate canonical context;
- create authority from history;
- change a historical Decision or version;
- persist versions automatically;
- infer missing historical truth;
- execute retention, archival, deletion, or forgetting;
- invoke GraphRAG, Context Graph, embeddings, vector storage, Knowledge
  reasoning, broad RAG, agents, or autonomous reasoning.

---

## Acceptance Criteria

- A valid plan deterministically freezes exact governed source references.
- Plan drift blocks capture rather than regenerating intent.
- Capture produces an immutable content-free `contextos.context.version/1`.
- Repeated capture of an unchanged plan produces the same identity.
- Source change affects current applicability without erasing historical
  identity.
- Unrelated repository advancement does not make unchanged selected context
  stale.
- Repository tip, selected-source currentness, profile currentness, target
  canonical currentness, and historical exactness remain independently visible.
- Historical Git evidence is optional and explicitly implementation-specific.
- Activation and Context Version evidence remain distinct.
- Parent/supersession lineage does not rewrite prior versions.
- Unknown historical sources remain explicit.
- Reports are human-readable and pure machine-readable objects.
- The capability is read-only and stdlib-only.
