# 1.0 — Context OS Architecture

## Canonical Definition

The first-principles architectural definition of Context OS is anchored in
[`0.8 Context OS GENESIS`](../0.x_foundations/0.8_COS_GENESIS.md). This
document expands that definition into the system architecture.

Context OS is an **Organizational Context Runtime** for human-agent systems.

It is the governable operating layer that turns fragmented organizational
information into structured context, durable memory, accountable action, and
coherent human-agent collaboration.

Context OS is not merely a documentation framework. Documentation is one
surface of the system. The system itself is the runtime model, governance
model, memory model, agent model, and activation model that make context
usable in real work.

The shortest definition is:

> Context OS makes organizational context operational.

The fuller definition is:

> Context OS is a product, architecture, and operating model that helps an
> organization assess, bootstrap, construct, activate, learn from, and reason
> over its context under governance.

---

## What Context OS Is

Context OS is five things at once:

| Perspective | Definition |
|---|---|
| Product | A user-facing system that answers what context exists, what is missing, how ready the organization is, and what should happen next |
| Architecture | A layered contextual infrastructure system built around SSOT, memory, runtime engines, governance, and activation |
| Runtime | A set of engines that discover, assess, construct, validate, graph, activate, and evolve context |
| Organizational system | A governable operating model for decisions, ownership, policies, missions, and memory |
| Human-agent system | The contextual substrate that lets humans and agents collaborate with shared constraints, evidence, and authority |

Context OS remains an Organizational Context Runtime. That phrase is the
canonical product category. GENESIS defines the first-principles model; this
architecture expands the category into a system-of-systems model.

---

## Product Journey

The canonical product journey is:

```text
Assess -> Bootstrap -> Construct -> Activate -> Learn -> Reason
```

| Step | Product question | Runtime emphasis |
|---|---|---|
| Assess | What context exists here, what is missing, and what should I do next? | Context Readiness Engine + Validator Engine |
| Bootstrap | How do I create a minimum governed Context OS home? | Runtime CLI + governance scaffolding |
| Construct | How do I turn sources into usable context? | Discovery Engine + Knowledge Engine + Context Builder |
| Activate | How does context reach tools, humans, and agents? | Activation Layer + Human-Agent Runtime |
| Learn | How does context stay current? | Context Memory + Validator Engine + governance loops |
| Reason | How does context improve decisions and execution? | Context Graph + memory + governed agents |

Context Readiness is the first product capability because it transforms a
repository from opaque files into an understandable readiness state without
writing to it.

---

## System-of-Systems Model

Context OS consists of eight canonical layers:

1. Context Foundation
2. Memory Layer
3. Governance Layer
4. Runtime Engine Layer
5. Context Graph Layer
6. Agent System Layer
7. Capability, Skill, and Tool Layer
8. Activation Layer

The SSOT remains the authoritative system of record. The Runtime reads from,
derives from, validates, and proposes changes to the SSOT under governance.
The Context Graph and activation surfaces are derived or operational views;
they do not replace the SSOT.

```text
Organizational Reality
        |
        v
Discovery Engine + Knowledge Engine
        |
        v
Context Readiness Engine -> Validator Engine
        |
        v
Context Builder -> SSOT -> Context Memory
        |
        v
Context Graph
        |
        v
Activation Layer
        |
        v
Humans + Agents + Systems
```

Governance surrounds every layer. No layer is allowed to silently mutate
authoritative context.

---

## 1. Context Foundation

The Context Foundation defines the conceptual substrate:

- Context Theory
- Context Principles
- Context Construction Loops
- Minimum Operational Map (MOM)
- Single Source of Truth (SSOT)
- Document Taxonomy
- Product and operational models

The foundation answers:

> What should context be, and how should it be structured?

The foundation is not sufficient by itself. It becomes operational only when
the Runtime can assess, validate, build, activate, and evolve it.

---

## 2. Memory Layer

Context OS treats memory as governed context over time.

The memory model is defined by:

- belief states: `observed`, `inferred`, `hypothesis`, `verified`,
  `deprecated`
- temporal context
- working memory
- project memory
- organizational memory
- context versions and retention rules

Context Memory is the canonical destination for concepts previously explored
under Memor.IA. Memor.IA is not a separate product line inside Context OS; its
durable-memory concerns converge into Context Memory.

Memory answers:

> What did we know, when did we know it, why did we believe it, and what
> superseded it?

---

## 3. Governance Layer

Governance makes context trustworthy.

It defines:

- ownership
- authority levels
- policy inheritance
- Definitions of Ready and Done
- change proposals
- decision records
- accountability ledger
- validation gates

Governance is not an approval decoration placed after the work. It is the
control plane for context mutation, agent authority, runtime activation, and
memory promotion.

The governing principle is:

> Evidence over trust.

---

## 4. Runtime Engine Layer

The Runtime Engine Layer operationalizes context through seven primary
components:

| Component | Responsibility |
|---|---|
| Discovery Engine | Inventory and map structured local or connected sources |
| Knowledge Engine | Interpret unstructured organizational knowledge |
| Context Readiness Engine | Assess what context exists, what is missing, readiness level, and next actions |
| Context Builder | Compose discovered and interpreted signals into governed MOM/SSOT drafts |
| Validator Engine | Protect contextual integrity through deterministic validation rules |
| Context Graph | Derive navigable relationships from authoritative context |
| Activation Layer | Deliver governed context into humans, agents, tools, and workflows |

The Runtime CLI is the human and automation entry surface for these engines.
It must wrap engine behavior rather than reimplement engine logic.

---

## 5. Context Graph Layer

The Context Graph represents relationships among context artifacts, entities,
decisions, systems, capabilities, evidence, and missions.

The graph is derived. It is not authoritative.

The graph exists to:

- improve navigation
- support retrieval
- expose relationships
- help agents reason over context
- support memory traversal

The SSOT remains the authority. The graph is an operational index and
reasoning surface.

---

## 6. Agent System Layer

The Agent System is defined by the Agentic Operating Model.

Agents are role-based units of organizational intelligence. They operate over
shared context, within declared authority, and under governance.

The agent system includes:

- Orchestrator
- Context Guardian
- Analysis Agent
- Execution Agent
- Verification Agent
- dynamic agents instantiated from capability pools

The Human-Agent Runtime is the operational composition of:

- Agentic Operating Model
- Human-Agent Authority Model
- Mission Contract
- Capability Model
- Skillbox
- Toolbox
- Activation Layer

The Human-Agent Runtime does not replace Context OS. It is the way Context OS
becomes coordinated human-agent work.

---

## 7. Capability, Skill, and Tool Layer

Context OS separates responsibility from execution primitives:

| Concept | Meaning |
|---|---|
| Role | Accountable job description for a human or agent |
| Capability | Domain of expertise or problem-solving capacity |
| Skill | Cognitive or procedural ability available to roles |
| Tool | Permissioned access to an external system or action surface |
| Mission | Bounded unit of work performed under context and authority |

Capabilities are selected dynamically. Skills enable reasoning or execution.
Tools create side effects and therefore require stricter governance.

This separation prevents a common failure mode: treating a powerful tool or
model as if it were accountable intelligence.

---

## 8. Activation Layer

Activation turns context into operational capability.

Activation surfaces may include:

- Runtime CLI
- IDE integrations
- agent workspaces
- workflow systems
- automation platforms
- future product interfaces

Activation is not merely integration. It is governed context delivery. A
surface is activated only when it knows what context it is using, where that
context came from, what authority applies, and what actions are allowed.

## Canonical Runtime Components

The canonical Runtime component list is:

1. Discovery Engine
2. Knowledge Engine
3. Context Readiness Engine
4. Context Builder
5. Validator Engine
6. Context Graph
7. Activation Layer
8. Runtime CLI

These components are released progressively through the product journey. They

## Lineage and Convergence

Several related initiatives informed Context OS. Their concepts now converge
inside the canonical architecture:

| Initiative | Canonical relationship |
|---|---|
| Knowledge Mapper | Converges into the Discovery Engine: source inventory, system mapping, ownership mapping, and relationship identification |
| Memor.IA | Converges into Context Memory: belief states, temporal memory, context versions, retention, and organizational memory |
| Cocora | Converges into the Knowledge Engine, Activation Layer, and Human-Agent Runtime: interpretation, interaction, and agent-facing context delivery |
| Lukspeed | Serves as an operational laboratory and dogfooding environment for applying Context OS concepts in real work |

These are not parallel architectures inside the repository. They are sources
of validated concepts that have been absorbed into Context OS.

## Architecture vs Runtime

Context OS has two complementary architectural views:

- [`1.0 Context OS Architecture`](1.0_COS_Architecture.md) defines the
  canonical system-of-systems model.
- [`1.4 Context Runtime Architecture`](1.4_COS_Context_Runtime_Architecture.md)
  details the Runtime component view.

The Runtime does not replace the framework. The framework defines how context
is structured and governed. The Runtime makes that context assessable,
constructable, activatable, learnable, and usable by humans and agents.

---

## Non-Negotiable Constraints

- The SSOT is authoritative.
- The Context Graph is derived.
- The Runtime must not silently mutate context.
- All context changes are governed and auditable.
- Readiness assessment is read-only in v0.3.
- Knowledge interpretation must preserve provenance.
- Agents operate under explicit authority.
- Tools are permissioned and environment-dependent.
- Memory promotion requires evidence.
- Activation must respect validation and governance gates.

---

## Long-Term Vision

The long-term vision is not a documentation system, a standalone agent
framework, or a SaaS wrapper around prompts.

The long-term vision is an Organizational Context Runtime:

- context as infrastructure
- memory as governed context over time
- governance as the control plane
- agents as accountable roles
- capabilities, skills, and tools as composable execution primitives
- activation as governed delivery into real work

In a human-agent organization, intelligence does not scale merely because
models improve. It scales when context is explicit, governed, remembered,
activated, and continuously improved.

Context OS is the system that makes that possible.
