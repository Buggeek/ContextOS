# 3.6 — Human-Agent Authority Model

## Purpose

This document defines **who is allowed to do what** in a Context OS Runtime:
the authority boundaries between humans and agents, autonomy levels, approval
matrix, escalation rules, trust boundaries, and accountability.

It complements [`3.1_COS_Agentic_Operating_Model.md`](3.1_COS_Agentic_Operating_Model.md),
which defines *how* work is performed, by declaring *what is permitted* and
*who is accountable*.

This artifact is **mandatory before any agent-mediated execution is
implemented**. Without it, autonomy is implicit and accountability is
ambiguous.

---

## Core Principles

1. **Accountability is human.** Every outcome has a human owner of record.
2. **Authority is explicit.** No agent acts at an authority level it has not
   been explicitly granted.
3. **Authority is contextual.** Authority is scoped to an artifact class, a
   mission, and a runtime environment — never global.
4. **Authority is revocable.** Any granted authority can be revoked without
   architectural change.
5. **Trust is bounded by evidence.** Autonomy increases only when prior
   actions produced verifiable, traceable evidence.

---

## Autonomy Levels

Context OS defines six autonomy levels. Every agent capability is bound to a
level per artifact class.

| Level | Name | Description | Human role |
|---|---|---|---|
| L0 | None | Agent has no capability for this action | n/a |
| L1 | Suggest | Agent proposes; nothing is written | Reviewer |
| L2 | Draft | Agent writes to a draft surface (branch, scratch, proposal) | Approver |
| L3 | Execute-with-approval | Agent executes; effect is staged pending approval | Approver |
| L4 | Execute-autonomously | Agent executes immediately within declared bounds | Auditor |
| L5 | Self-improve | Agent may also modify its own policies/skills within governance | Auditor |

**Default starting level for any new capability:** L1.

**Promotion path:** L1 → L2 → L3 → L4 requires a documented decision record
citing accumulated evidence of correct behavior. L5 requires an additional
governance review.

## Approval Matrix

Authority is declared per **artifact class** and per **action**.

| Artifact class | Read | Propose | Modify (draft) | Modify (apply) | Delete |
|---|---|---|---|---|---|
| Foundations (`docs/0.x/`) | All agents | Analysis | Analysis (L2) | **Maintainer only** | **Maintainer only** |
| Architecture (`docs/1.x/`) | All agents | Analysis | Analysis (L2) | **Maintainer only** | **Maintainer only** |
| Taxonomy (`docs/2.x/`) | All agents | Analysis | Analysis (L2) | **Maintainer only** | **Maintainer only** |
| Operation (`docs/3.x/`) | All agents | Analysis | Analysis (L2) | **Maintainer only** | **Maintainer only** |
| Adoption (`docs/4.x/`) | All agents | Analysis | Analysis (L2) | Maintainer | Maintainer |
| Strategy (`docs/5.x/`) | All agents | Analysis | Analysis (L2) | **Maintainer only** | **Maintainer only** |
| SSOT MOM (`SSOT/S.1, P.1, A.1, A.4, G.1, G.2`) | All agents | Analysis | Execution (L3) | Maintainer | **Forbidden** |
| SSOT Roadmap (`SSOT/P.2_Product_Roadmap.md`) | All agents | Product Owner | Execution (L3) | Product Owner | Forbidden |
| SSOT Epics (`SSOT/epics/EPIC-*`) | All agents | Orchestrator | Execution (L3) | Product Owner | Forbidden |
| SSOT User Stories (`SSOT/E.*`) | All agents | Orchestrator | Execution (L3) | Product Owner | Product Owner |
| Decision Records | All agents | Orchestrator / Analysis | n/a (immutable once recorded) | n/a | **Forbidden** |
| Runtime configuration | Runtime Owner only | — | — | Runtime Owner | Runtime Owner |
| Source code (future) | Execution | Execution | Execution (L3) | Maintainer or CI gate | Maintainer |

**Forbidden** means no agent, at any autonomy level, may perform the action.
The only path is a human change with a decision record.

## Trust Boundaries

Trust is bounded along five axes. Every capability declares its bounds.

| Axis | Bound |
|---|---|
| **Read scope** | Which artifact classes the agent may read |
| **Write scope** | Which artifact classes the agent may write |
| **Side-effect scope** | Which external systems the agent may touch |
| **Resource scope** | Compute / token / time ceilings |
| **Mission scope** | Which mission(s) the granted authority applies to |

Any action outside declared bounds is a runtime violation and triggers
Escalation.

---

## Escalation Rules

Escalation is **mandatory** when any of the following is true:

1. Context required for the action is missing or contradictory.
2. The action would exceed declared autonomy level.
3. The action would exceed declared trust bounds.
4. Validation reports a failure the agent cannot resolve within scope.
5. The Mission Packet success criterion cannot be met.
6. Confidence in the proposed action is below the declared threshold.

### Escalation target order

1. Orchestrator (always first — single interface).
2. Mission Owner (the human who initiated the mission).
3. Role Owner (the human who owns the agent role contract).
4. Governance Role (when policy interpretation is required).

Escalations are recorded as runtime events; silent escalation is forbidden.

---

## Accountability Ledger

For every action taken by an agent at L3 or above, the runtime records:

- `mission_id`
- `agent_role` and `capability`
- `autonomy_level` granted
- `human_owner` (mission owner)
- `evidence_link` (artifact, commit, decision record)
- `outcome` (`accepted`, `rejected`, `escalated`, `failed`)

The ledger is append-only and is the source of truth for the
Governance Lifecycle audit (3.4 §7).

---

## Role-Specific Defaults

| Role | Default autonomy | Notes |
|---|---|---|
| Orchestrator | L3 on coordination, L1 on artifact mutation | Never decides product outcomes |
| Analysis Agent | L2 across all doc classes | May write drafts; never applies |
| Execution Agent | L3 on draft surfaces; L2 elsewhere | Applies only via approval gates |
| Verification Agent | L2 on evidence artifacts; L4 read-only audits | Cannot modify the artifact it verifies |
| Context Guardian | L3 on SSOT integrity actions (link fix, taxonomy fix) | Cannot mutate semantic content |

Specific role contracts in
[`docs/3.x_operation/3.2_agent_system/roles/`](3.2_agent_system/roles/) may
narrow these defaults but never broaden them without a governance decision.

## Decision Authority by Lifecycle Stage

| Lifecycle stage | Decision authority |
|---|---|
| Strategy / Vision | Leadership (human) |
| Product Decide (3.5 §6) | Product Owner (human) |
| Mission Plan acceptance | Mission Owner (human) |
| Mission Verify outcome | Verification Agent → Mission Owner |
| Mission Close | Orchestrator (with Mission Owner confirmation) |
| Release approval | Release Owner (human) |
| Governance decision | Governance Role (human) |
| Context evolution apply | Context Guardian (with Maintainer for breaking changes) |
| Runtime upgrade | Runtime Owner (human) |

Agents may **propose** at any of these stages; they may not **decide**.

---

## Conflict Resolution

When two authorities conflict (for example, Product Owner and Maintainer
disagree on a roadmap change that crosses governance policy):

1. Issue is captured as a Decision Record.
2. Issue is routed to the Governance Lifecycle.
3. Resolution is binding and recorded.
4. The relevant policy or authority bound is updated if the conflict
   reveals a gap.

## Memory Retention Authority

Organizational Memory retention specializes, but does not replace, this
authority model. Classification and transition proposals begin at L1; policy
drafts use L2; approved non-destructive retention transitions require an exact
L3 human decision. Legal/compliance holds may be placed or released only by
the human role designated by applicable policy.

Redaction, minimization, and content removal have no autonomous-agent default.
They require a separate destructive-operation contract and explicit human
authority. Retention authority never grants authority to change canonical
truth, and Context Construction authority never grants authority to delete
memory.

See
[`1.5.13 Organizational Memory Retention Governance Contract`](../1.x_architecture/1.5_runtime_contracts/1.5.13_Organizational_Memory_Retention_Governance_Contract.md).

---

## Anti-Patterns

- Granting global authority instead of artifact-scoped authority.
- Promoting an agent to L4 without an accountability ledger trail.
- Implicit escalation (agent stops without notifying Orchestrator).
- Agents deciding product outcomes.
- Maintainer-only actions performed by agents through indirect paths.
- "Read-only" agents writing through tool side effects.
