# 3.7 — Governance Protocol

## Purpose

This document defines the **runtime-level governance protocol** of Context OS.

It consolidates and operationalizes the three governance surfaces that
existed in earlier layers:

- [`ops/AGENT_RULES.md`](../../ops/AGENT_RULES.md) — agent-facing rules
- [`SSOT/G.1_Definition_of_Ready.md`](../../SSOT/G.1_Definition_of_Ready.md) — readiness gates
- [`SSOT/G.2_Definition_of_Done.md`](../../SSOT/G.2_Definition_of_Done.md) — completion gates

…into a single runtime contract describing **policy inheritance**, **artifact
ownership**, **runtime permissions**, the **change-proposal protocol**, and
the **audit trail**.

Governance Protocol is the runtime interpretation layer that turns those
markdown artifacts into enforced behavior.

---

## 1. Layers and Inheritance

Governance is layered. Each layer can constrain but not relax the layer
above.

```
Doctrine (foundations)
   │
   ▼
Organizational Policy   ◄── set by Maintainers
   │
   ▼
Project Policy           ◄── set by Project / Product Owners
   │
   ▼
Mission Policy            ◄── set in the Mission Packet
   │
   ▼
Action                   ◄── executed by agents within authority bounds
```

Rules:

1. **No relaxation downward.** A project cannot grant authority broader than
   organizational policy permits.
2. **Explicit inheritance.** Every policy declares `inherits_from`.
3. **Composable.** Multiple policies can apply; conflicts resolve by
   precedence: Mission < Project < Organizational < Doctrine, with the
   **most restrictive** wins on autonomy and the **most permissive on
   read-only** access.
4. **Versioned.** Policies are versioned and immutable on update (new
   version supersedes old; old retained for audit).

## 2. Artifact Ownership

Every artifact in `docs/`, `SSOT/`, `ops/`, `templates/`, and any project
SSOT must declare an owner.

```yaml
artifact_meta:
  path: <relative path>
  class: foundations | architecture | taxonomy | operation | adoption |
         strategy | ssot-mom | ssot-roadmap | ssot-epic | user-story |
         decision | runtime-config | source-code
  owner: <id>                # accountable role or person
  contributors: [<id>...]    # optional
  inherits_policy_from: <policy id or path>
```

Ownership is enforced by the Validator `ownership` rule
([`1.5.1`](../1.x_architecture/1.5_runtime_contracts/1.5.1_Validator_Contract.md)).

| Artifact Class | Default Owner |
|---|---|
| Foundations / Architecture / Taxonomy | Maintainers |
| Operation / Adoption / Strategy | Maintainers + Runtime Owner |
| SSOT MOM | Product Owner |
| SSOT Roadmap | Product Owner |
| SSOT Epics | Product Owner |
| User Stories | Mission Owner |
| Decision Records | Decision Author + Governance roster |
| Runtime configuration | Runtime Owner |
| Source code (future) | Code Owner |

Defaults are inherited from
[`3.6 Human-Agent Authority Model`](3.6_COS_Human_Agent_Authority_Model.md).

## 3. Runtime Permissions

A **runtime permission** binds a role, a capability, an artifact class, an
autonomy level, and a scope.

```yaml
permission:
  role: <role id>
  capability: <capability id>
  artifact_class: <class>
  autonomy: L0 | L1 | L2 | L3 | L4 | L5
  scope:
    read: [<path or selector>...]
    write: [<path or selector>...]
    side_effects: [<system or surface>...]
    resources: { tokens: <int>, time: <duration>, compute: <profile> }
  required_evidence: [<evidence kind>...]
  expires_at: <iso8601 or null>
```

Rules:

1. **Default deny.** Absence of permission means no authority.
2. **Bounded scope.** Permissions must declare read/write scope; wildcards
   require explicit Governance approval.
3. **Time-bounded if elevated.** L3+ permissions should declare
   `expires_at` whenever practical.
4. **Evidence requirements.** Some permissions require attached evidence
   (e.g., verification reports) before write.
5. **Logged.** Permission grants and uses emit `authority.*` events
   (see [`1.5.5`](../1.x_architecture/1.5_runtime_contracts/1.5.5_Runtime_Event_Model.md)).

## 4. Change-Proposal Protocol

Any change to SSOT, governance configuration, or runtime configuration flows
through the **Change-Proposal Protocol**.

```
1. Propose      → producer (human or agent) emits a Change Proposal
2. Stage        → proposal placed in staging area; not yet applied
3. Validate     → Validator runs in `gate` mode against the staged result
4. Review       → required reviewers per artifact class and autonomy level
5. Decide       → accept (apply) | reject | request-changes
6. Apply        → Context Guardian integrates into SSOT
7. Record       → Decision Record + Accountability Ledger entry written
8. Emit         → `governance.decision.recorded` + `context.artifact.updated`
```

### Change Proposal shape

```yaml
change_proposal:
  schema: contextos.change.proposal/1
  id: <ulid>
  mission_id: <ulid or null>
  author: <id>
  authority:
    role: <role>
    level: L0..L5
  rationale: <multi-line>
  artifact_class: <class>
  changes:
    - path: <path>
      diff_ref: <handle to diff>
  evidence_refs: [<artifact or report ref>...]
  reviewers_required: [<role>...]
  created_at: <iso8601>
  status: proposed | staged | validated | reviewing | decided | applied | rejected
```

### Required reviewers by class

| Class | Required reviewers |
|---|---|
| Foundations | ≥1 Maintainer |
| Architecture | ≥1 Maintainer + Runtime Owner |
| Taxonomy | ≥1 Maintainer |
| Operation | Runtime Owner |
| Adoption | Runtime Owner |
| Strategy | Product Owner + ≥1 Maintainer |
| SSOT MOM | Product Owner |
| SSOT Roadmap | Product Owner |
| SSOT Epics | Product Owner |
| User Stories | Mission Owner |
| Decision Records | Author + ≥1 named decision participant |
| Runtime configuration | Runtime Owner |

Reviewers may be the same person playing multiple roles; one human cannot
serve as the **only** reviewer for a class where they are also the author
above autonomy L2.

## 5. Decision Records

Every accepted change above L2 produces a **Decision Record**.

```yaml
decision:
  schema: contextos.decision/1
  id: <ulid>
  title: <human-readable>
  context_version: <ulid>      # see 0.7 Context Versioning
  proposal_id: <ulid>
  decided_by: [<id>...]
  decided_at: <iso8601>
  rationale: <multi-line>
  alternatives_considered: [<short list>]
  consequences: [<short list>]
  links: [<artifact or graph selector>...]
```

Decision Records are immutable. Reversals create a **new** decision that
references the reversed one.

## 6. Accountability Ledger

The Accountability Ledger is an **append-only** event stream filtered to
governance-relevant events:

- All `governance.*` events.
- All `authority.*` events.
- All `mission.*` terminal events.
- All `validation.blocked` and `validation.fatal` events.
- All `context.artifact.updated` for artifacts where `class ∈ {foundations,
  architecture, taxonomy, ssot-mom, ssot-roadmap, ssot-epic, decision,
  runtime-config}`.

The ledger is the audit trail. It must be queryable by `mission_id`,
`role`, `artifact path`, and time range.

## 7. Drift, Violations, Escalation

| Condition | Response |
|---|---|
| Authority bound exceeded | Action rejected; `governance.violation.detected` emitted; mission `escalated` |
| Hypothesis past closure window | `drift.detected`; Product Owner notified |
| Discovery vs SSOT conflict | `discovery.conflict.detected`; Change Proposal required |
| Ownership coverage gap | Validator `error`; mission to assign owner |
| Decision Record missing for L3+ change | Validator `error`; block on next `gate` run |

Escalation routes inherit the order declared in
[`3.6 Authority Model`](3.6_COS_Human_Agent_Authority_Model.md) §Escalation.

## 9. Anti-Patterns

- Granting blanket L3+ permissions instead of bounded `scope`.
- Editing SSOT directly without a Change Proposal once Runtime is active.
- Letting reviewers be implicit ("someone will review it").
- Missing Decision Records for L3+ changes.
- Treating policy version updates as silent edits.
