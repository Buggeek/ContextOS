# 3.5 — Product Operating Model

## Purpose

This document defines how Context OS organizations operate the **Product
Lifecycle** declared in
[`3.4_COS_Operational_Lifecycle.md`](3.4_COS_Operational_Lifecycle.md).

It integrates hypothesis-driven development, Lean Startup, Design Thinking, and
Continuous Discovery into a single product operating model that produces
SSOT-grade outputs.

It is **not** a methodology choice. It is the canonical model used by the
Orchestrator and Product Owner to translate strategy into validated execution.

---

## Core Principle

> **No product surface advances without verified evidence.**

Every product artifact in SSOT is explicitly tagged as `Hypothesis` or
`Verified`. The Product Operating Model is the machinery that moves artifacts
across that boundary.

---

## The Product Loop

```
                  ┌───────────────────────────┐
                  │  Strategy (S.1, P.1)      │
                  └──────────────┬────────────┘
                                 ▼
   ┌─────────────────────────────────────────────────────────┐
   │                                                         │
   │   1. Frame      → problem, user, constraint             │
   │   2. Discover   → research, interviews, signals         │
   │   3. Hypothesize → testable claim + success criterion   │
   │   4. Build      → smallest valuable artifact            │
   │   5. Validate   → evidence vs criterion                 │
   │   6. Decide     → promote / iterate / kill              │
   │   7. Propagate  → SSOT update, roadmap reorder          │
   │                                                         │
   └──────────────┬──────────────────────────────────────────┘
                  ▼
              Feedback Lifecycle ──► Learning Lifecycle
```

Each iteration of the loop is owned by a **Product Mission** instantiated via
the Mission Lifecycle (3.4 §3).

## Stages

### 1. Frame
- **Input:** vision, strategic intent, observed signal.
- **Output:** problem statement, target user, hard constraints.
- **Owner:** Product Owner. Analysis Agent assists with prior-art synthesis.
- **DoR for next stage:** problem statement is falsifiable.

### 2. Discover
- **Input:** problem statement.
- **Methods:** interviews, observation, market scans, log analysis, prior
  mission learnings.
- **Output:** evidence inventory tagged with provenance and confidence.
- **Owner:** Product Owner. Knowledge Engine and Discovery Engine assist when
  the signal lives in connected systems.

### 3. Hypothesize
- **Input:** evidence inventory.
- **Output:** explicit hypothesis with the form:
  *"We believe `X`. We will know we are right when we observe `Y` within
  `Z`."*
- **Constraint:** every hypothesis must declare its **success criterion** and
  **kill criterion**.
- **SSOT:** stored as a Hypothesis node referenced by the relevant
  `P.1`/`P.2`/`P.5` artifact.

### 4. Build
- **Input:** hypothesis + smallest viable artifact definition.
- **Output:** the artifact (prototype, experiment, A/B test, internal tool,
  ADR).
- **Constraint:** build cost is bounded by the cost of being wrong.

### 5. Validate
- **Input:** build output + measurement plan.
- **Output:** evidence against the success criterion.
- **Owner:** Verification Agent. Analysis Agent interprets ambiguous evidence.
- **Rule:** evidence is recorded even when it contradicts the hypothesis.

### 6. Decide
- **Outcomes:**
  - `Promote` — hypothesis becomes `Verified`; roadmap updates.
  - `Iterate` — adjust hypothesis or build; restart at stage 3.
  - `Kill` — hypothesis recorded as falsified; learnings captured.
  - `Defer` — paused with explicit re-evaluation trigger.
- **Owner:** Product Owner (human decision; never autonomous).

### 7. Propagate
- **Output:** SSOT updates (`P.1`, `P.2`, `P.5`, decision records).
- **Triggers:** Feedback Lifecycle (signals back to strategy), Learning
  Lifecycle (lessons), Release Lifecycle (when validated work ships).

## Methodology Integration

The Product Loop is methodology-agnostic but explicitly composable with:

### Design Thinking
- `Empathize` and `Define` map to stages 1–2 (Frame, Discover).
- `Ideate` and `Prototype` map to stages 3–4 (Hypothesize, Build).
- `Test` maps to stage 5 (Validate).

### Lean Startup
- Build–Measure–Learn maps to stages 4–5–6 (Build, Validate, Decide).
- Persevere/Pivot/Kill maps to the Decide outcomes.

### Continuous Discovery
- Stage 2 (Discover) is always-on, not phase-gated.

Context OS does not enforce a methodology; it enforces the **artifacts and
transitions** that any of these methodologies produce.

## Hypothesis vs Verified

| Field | Hypothesis | Verified |
|---|---|---|
| `status` | `hypothesis` | `verified` |
| `confidence` | low / medium / high (qualitative) | evidence-backed |
| `success_criterion` | required | satisfied |
| `evidence` | optional, partial | required, traceable |
| `decision_record` | optional | required at promotion |
| `kill_criterion` | required | n/a |

This distinction is **mandatory metadata** on every product artifact in SSOT.
Agents must respect it: reasoning over a `hypothesis` artifact must not produce
`verified` downstream artifacts.

## Technical Debt Governance

Technical debt is treated as a product artifact, not an engineering nuisance.

- Each debt item is captured as a structured entry referenced by `A.1`,
  `P.2`, or an epic.
- Each entry declares: origin, blast radius, interest cost, retirement
  trigger.
- Retirement enters the same Product Loop (Frame → … → Propagate).
- The Roadmap (`P.2`) reserves explicit capacity for debt retirement per
  version. Capacity policy lives in the Governance Protocol.

---

## Organizational Prioritization

Prioritization is governed by three explicit dimensions:

1. **Strategic fit** — alignment with `S.1` and current version goal.
2. **Evidence weight** — strength of the underlying validated learning.
3. **Cost of delay** — opportunity cost weighted by reversibility.

Prioritization decisions are recorded in the Roadmap and are themselves
auditable artifacts (Governance Lifecycle).

---

## Roles in the Product Operating Model

| Role | Responsibility |
|---|---|
| Product Owner (human) | Frame, Hypothesize, Decide; owns the artifact |
| Orchestrator | Runs the loop as Mission Lifecycle; assembles agent teams |
| Analysis Agent | Discover, evidence interpretation, prior-art synthesis |
| Execution Agent | Build artifacts, instrument measurement |
| Verification Agent | Validate evidence, enforce success criterion |
| Context Guardian | Propagate updates into SSOT, prevent drift |
| Knowledge Engine | Surface relevant prior knowledge during Discover |
| Discovery Engine | Surface system-level evidence (usage, metrics) |

Authority boundaries follow
[`3.6_COS_Human_Agent_Authority_Model.md`](3.6_COS_Human_Agent_Authority_Model.md).

---

## Anti-Patterns

- Building before hypothesizing.
- Hypothesis without a kill criterion.
- Promoting evidence from `hypothesis` to `verified` without a decision
  record.
- Roadmap items with no linked hypothesis or no linked validated evidence.
- Agents making the Decide step autonomously.
- Treating tech debt as outside the product loop.
