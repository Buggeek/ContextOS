# 3.4 — Operational Lifecycle

## Purpose

This document defines the **canonical lifecycles** that govern how a Context OS
organization operates over time.

While [`0.5_COS_Context_Construction_Loops.md`](../0.x_foundations/0.5_COS_Context_Construction_Loops.md)
defines how context is *constructed*, and
[`3.1_COS_Agentic_Operating_Model.md`](3.1_COS_Agentic_Operating_Model.md)
defines how work is *executed*, this document defines the **lifecycles inside
which both happen**.

Lifecycles are not phases. They are recurring, observable, governed processes
with explicit triggers, inputs, outputs, owners, and success criteria.

---

## Lifecycle Catalog

Context OS recognizes nine canonical lifecycles. Each one is owned by a clear
party, produces or updates SSOT artifacts, and emits runtime events that other
lifecycles can react to.

| # | Lifecycle | Primary Owner | Cadence |
|---|---|---|---|
| 1 | Organization Lifecycle | Leadership | Strategic |
| 2 | Product Lifecycle | Product Owner | Continuous |
| 3 | Mission Lifecycle | Orchestrator | Per mission |
| 4 | Release Lifecycle | Execution Agent / Release Owner | Per release |
| 5 | Feedback Lifecycle | Verification Agent / Support | Continuous |
| 6 | Learning Lifecycle | Context Guardian | Continuous |
| 7 | Governance Lifecycle | Maintainers / Governance Role | Event-driven |
| 8 | Runtime Lifecycle | Runtime Owner | Per environment |
| 9 | Context Evolution Lifecycle | Context Guardian | Continuous |

Product Lifecycle internals are detailed in
[`3.5_COS_Product_Operating_Model.md`](3.5_COS_Product_Operating_Model.md).

## 1. Organization Lifecycle

### Purpose
Anchor and evolve the organization's intent, principles, and constraints.

### Stages
`Anchor → Discover → Operate → Evolve → Re-anchor`

### Triggers
- New organization or product line
- Major strategic reset
- Introduction of agents into decision-making
- Acquisition, restructuring, pivot

### Inputs
Leadership intent, market signals, strategic constraints.

### Outputs (SSOT)
- `S.1_Vision`
- `G.1_Definition_of_Ready`, `G.2_Definition_of_Done`
- Principles and non-negotiable constraints

### Owner
Leadership (human-accountable, agent-assisted).

### Success Criteria
Vision stable, constraints explicit, every other lifecycle can cite an anchor.

### Linked Loops
[Loop 0 — Why Anchor](../0.x_foundations/0.5_COS_Context_Construction_Loops.md).

---

## 2. Product Lifecycle

### Purpose
Move product surfaces from hypothesis to verified, then to scaled operation.

### Stages
`Hypothesis → Discovery → Build → Validate → Scale → Retire`

### Triggers
- New product hypothesis
- Customer signal
- Strategic bet

### Inputs
Vision, customer feedback, market evidence, technical feasibility.

### Outputs (SSOT)
- `P.1_Product_Map`
- `P.2_Product_Roadmap`
- `P.5_Epic_[Name]`
- Validated hypotheses (Hypothesis → Verified transitions)

### Owner
Product Owner (human-accountable, Analysis + Execution agent-assisted).

### Success Criteria
Each product surface has a known hypothesis state and a path to verification.

### Detailed Model
See [`3.5_COS_Product_Operating_Model.md`](3.5_COS_Product_Operating_Model.md).

---

## 3. Mission Lifecycle

### Purpose
Translate intent into bounded, accountable execution.

### Stages
`Intent → Packet → Plan → Assemble → Execute → Verify → Integrate → Close`

| Stage | What happens | Owner |
|---|---|---|
| Intent | Human or upstream lifecycle declares the goal | Human |
| Packet | Mission Packet is created (goal, context refs, constraints, success criteria) | Orchestrator |
| Plan | Decomposition into tasks | Orchestrator |
| Assemble | Dynamic Team Assembly per task | Orchestrator |
| Execute | Specialized agents perform work | Execution Agent |
| Verify | Verification Agent validates against success criteria | Verification Agent |
| Integrate | Outputs merged into SSOT, context updated | Context Guardian |
| Close | Mission marked Done, learnings captured | Orchestrator |

### Triggers
Upstream lifecycle event (product, release, feedback, governance).

### Inputs
Mission Packet (see Runtime Contracts).

### Outputs (SSOT + Runtime)
- Updated execution artifacts (epics, user stories, ADRs)
- Mission event stream (closed mission, evidence, decisions)
- Context updates

### Owner
Orchestrator (single interface). Humans accountable; agents executing.

### Success Criteria
Every mission ends in `Done`, `Cancelled`, or `Escalated` — never silently
abandoned. Every outcome is traceable to a Mission Packet.

---

## 4. Release Lifecycle

### Purpose
Move validated work from build to operational use under governance.

### Stages
`Plan → Build → Validate → Stage → Propagate → Observe → Stabilize`

### Triggers
- Mission Lifecycle close at scope `release`
- Time-based cadence
- Hotfix demand

### Inputs
Verified mission outputs, governance approval, release criteria.

### Outputs (SSOT + Runtime)
- Release notes (structured)
- Updated `A.1 System Map` if architecture changed
- Release event in runtime event stream

### Owner
Release Owner (human-accountable). Execution Agent and Verification Agent
assist.

### Success Criteria
Release passes Definition of Done; runtime observability confirms expected
operational profile; rollback path is documented.

---

## 5. Feedback Lifecycle

### Purpose
Convert real-world signals into structured context updates and roadmap input.

### Stages
`Signal → Capture → Classify → Route → Integrate → Close`

### Triggers
- Customer support input
- Operational incident
- Monitoring/observability signal
- Internal usage feedback

### Inputs
Raw signals (tickets, incidents, metrics, conversations).

### Outputs (SSOT)
- Updated `P.1_Product_Map` or `P.2_Product_Roadmap`
- New epics or user stories (when justified)
- Decision Records when feedback leads to a strategic choice

### Owner
Verification Agent + Support function (human-accountable).

### Success Criteria
No high-signal feedback is dropped; every accepted signal is traceable to an
SSOT update or an explicit rejection record.

---

## 6. Learning Lifecycle

### Purpose
Make organizational learning explicit and reusable instead of tribal.

### Stages
`Observe → Capture → Generalize → Encode → Distribute → Reuse`

### Triggers
- Mission close (lessons captured)
- Incident retrospective
- Strategic reset
- Repeated pattern across missions

### Inputs
Mission close reports, retros, drift reports, agent post-mortems.

### Outputs (SSOT)
- Updates to `G.1`, `G.2`, principles, agent role contracts
- New skill or tool entries in `3.3_execution_primitives/`
- Updated Skillbox / Toolbox catalogs

### Owner
Context Guardian (human-accountable, agent-assisted).

### Success Criteria
A repeated learning never has to be rediscovered; every captured learning has
a target artifact and an owner.

---

## 7. Governance Lifecycle

### Purpose
Enforce contextual integrity, ownership, and policy across all other
lifecycles.

### Stages
`Policy → Review → Decision → Audit → Evolve`

### Triggers
- Change proposal (PR, mission output, agent-proposed mutation)
- Periodic audit
- Drift report
- Policy update

### Inputs
Proposed change + governing policy + DoR/DoD.

### Outputs (SSOT)
- Approved diffs (with reviewer trail)
- Decision Records
- Updated policies in `ops/AGENT_RULES.md` and Governance Protocol
  (see [`3.7_COS_Governance_Protocol.md`](3.7_COS_Governance_Protocol.md)
  when authored)

### Owner
Maintainers / Governance Role.

### Success Criteria
Every change to SSOT is traceable to a decision, an owner, and an applied
policy.

---

## 8. Runtime Lifecycle

### Purpose
Manage the operational lifecycle of a Context OS Runtime instance.

### Stages
`Install → Bootstrap → Activate → Operate → Upgrade → Retire`

### Triggers
- New organization or new project adopting Context OS
- Major Runtime version upgrade
- Decommission

### Inputs
Installation requirements, source registry, credentials, mode (greenfield /
brownfield / hybrid).

### Outputs (Runtime + SSOT)
- Runtime instance metadata
- Connector Manifest
- First-time MOM and SSOT (via Bootstrap)
- Runtime event stream

### Owner
Runtime Owner.

### Success Criteria
Each Runtime instance has a known maturity level
(see [`5.5_COS_Runtime_Maturity_Model.md`](../5.x_strategy/5.5_COS_Runtime_Maturity_Model.md)
when authored) and a documented upgrade path.

### Linked Adoption Flow
[`4.4_COS_Runtime_Bootstrap.md`](../4.x_adoption/4.4_COS_Runtime_Bootstrap.md)
and [`4.5_COS_Runtime_Installation.md`](../4.x_adoption/4.5_COS_Runtime_Installation.md)
(when authored).

---

## 9. Context Evolution Lifecycle

### Purpose
Keep context aligned with reality as the organization, product, and runtime
evolve.

### Stages
`Detect → Diagnose → Propose → Validate → Apply → Re-baseline`

### Triggers
- Drift detected by Validator Engine
- Operational signal from Feedback Lifecycle
- New verified evidence replaces a hypothesis

### Inputs
Drift reports, validation failures, new evidence, retro outcomes.

### Outputs (SSOT)
- Incremental updates to MOM
- Context change logs
- Hypothesis → Verified transitions

### Owner
Context Guardian.

### Success Criteria
SSOT lag behind reality stays below a defined threshold; no silent context
mutation.

## Lifecycle Interaction Map

```
Organization ─┬─► Product ──► Mission ──► Release ──► Observe
              │       ▲           │           │           │
              │       │           ▼           ▼           ▼
              │   Feedback ◄──────────── Operational signals
              │       │
              │       ▼
              └── Learning ──► Governance ──► Context Evolution
                                                      │
                                                      ▼
                                                Runtime Lifecycle
                                                (install → retire)
```

Each arrow is a runtime event. Event taxonomy is defined in the
**Runtime Event Model** under
[`docs/1.x_architecture/1.5_runtime_contracts/`](../1.x_architecture/) (Phase C).
